> 상태: **설계 + 로컬 검증 완료 / Supabase에는 아직 적용하지 않음**
> 파일: `supabase/migrations/0001_schema.sql` · `0002_rls.sql` · `0003_storage.sql`, 테스트 `supabase/tests/`
> 기준 정책: 사용자가 승인한 10개 항목(이메일 인증 필수, EXP 서버 검증, 예시 데이터 분리 등)

## 2. 테이블

| 테이블 | 용도 | 핵심 규칙 |
|---|---|---|
| `profiles` | 닉네임 | 가입 시 트리거가 자동 생성, 닉네임 2~12자(한글·영문·숫자·_), **대소문자 무시 유일** |
| `bakeries` | **유효한 빵집 목록** | 클라이언트 쓰기 불가. Edge Function이 카카오 REST API로 검증 후 등록 |
| `reviews` | 모험 일지 | 사용자당 빵집 1개(수정 가능), 별점 0.5 단위, 내용 1~500자, 사진 경로는 내 폴더만 |
| `posts` | 게시글 | 카테고리 5종 check, 제목 1~80자, 내용 1~2000자 |
| `comments` | 댓글 · 답글(1단계) | **수정 불가, 삭제만** |
| `post_likes` | 좋아요 | PK(글, 사용자) → 계정당 글별 1회 |
| `bakery_visits` | 다녀왔어요 | **본인만 조회**, EXP·도감·퀘스트와 무관 |

저장하지 **않는** 것: EXP, 레벨, 퀘스트 진행, 배지, 순위 → 모두 뷰/계산으로 도출 (점수 컬럼이 없어서 조작할 대상 자체가 없어요).

## 3. EXP · 레벨 서버 검증 (정책 3번의 구현)

| 요구 | 구현 | 검증 |
|---|---|---|
| 리뷰 작성 시 경험치 | 트리거가 `exp_review=true`를 **서버에서** 결정 | ✅ 리뷰 1개 = 30 + 첫 리뷰 퀘스트 20 = 50 |
| 수정만으로 추가 EXP 없음 | `exp_*`는 수정 불가(권한 + 트리거). 내용·별점 수정은 EXP에 영향 없음 | ✅ |
| 삭제 시 회수 | EXP가 리뷰에서 계산되므로 삭제하면 사라짐. 레벨도 같이 내려감 | ✅ 삭제 후 EXP 0 |
| 중복 지급 방지 | `unique(user_id, bakery_id)` → **같은 빵집 EXP는 평생 1회**. 같은 요청 재전송은 유니크 위반으로 거부 | ✅ |
| 클라이언트 임의 수정 불가 | `exp_review/exp_photo`에 INSERT·UPDATE 권한 없음 + 트리거가 덮어씀 | ✅ 직접 넣기·수정·남의 명의 insert 모두 거부 |
| 유효한 빵집 ID만 | `reviews.bakery_id → bakeries.id` 외래키 | ✅ 미등록 ID 거부 |
| 사진 EXP | **작성할 때 사진이 있었고 지금도 있을 때만 +10**. 나중에 붙여도 없음, 지우면 회수 | ✅ |

### 확정: 지급 횟수와 하루 상한
| 항목 | 확정 값 | 이유 |
|---|---|---|
| 같은 빵집 EXP | **평생 1회** (`unique`로 강제). 같은 빵집에 다시 쓰거나 고쳐도 EXP는 늘지 않아요 | 반복 작성·수정 파밍 불가 |
| 하루 **EXP** 상한 | **100 EXP** (리뷰·사진 EXP 합계, 한국 시간 자정 기준). 남은 EXP가 모자라면 저장은 되지만 EXP·퀘스트에 미반영. 퀘스트 보너스는 1회성이라 상한 밖 | 리뷰 3개(90) 또는 사진 리뷰 2개+일반 1개(100) 수준 |
| 하루 **작성** 상한 | 리뷰 20 · 게시글 10 · 댓글 50 · 좋아요 200 | 스팸 방지(EXP와 별개) |
| 레벨 속도 감각 | 레벨5(800 EXP)까지 최소 약 7일(퀘스트 보너스 100 포함) | **`public.game_settings` 표의 `daily_exp_cap` 값 하나**로 조정(아래 안내) |

- **상한 변경 방법**(앱 배포 불필요, 클라이언트는 못 바꿈): SQL Editor에서 `update public.game_settings set value = 150 where key = 'daily_exp_cap';` — 이후 작성분부터 적용돼요. 리뷰/사진 EXP(`review_exp`, `photo_exp`)도 같은 표에 있지만, 바꾸면 `src/constants/gameRules.js`도 함께 바꿔야 해요(테스트가 일치를 검사).
- 삭제 후 같은 빵집 재작성: 삭제 때 EXP가 회수되므로 **순증가 없음**(하루 상한 안에서만 다시 받음)
- 도감(발견)은 EXP 상한과 **별개**: 상한을 넘어 쓴 리뷰도 도감에는 반영돼요
- ⚠️ 한계: 사용자가 카카오 장소를 **실제로 방문했는지는 알 수 없어요**. "실제 존재하는 빵집"만 검증합니다. 방문 인증처럼 표시하지 않아요.

### 확정: 배지 정책
| 배지 종류 | 정책 |
|---|---|
| 키워드 배지(소금빵 마니아 · 크루아상 헌터 · 딸기 시즌 · 오픈런) | **현재 조건으로 재계산** (리뷰를 지우면 사라짐) — 현행 유지 |
| 정복 배지('전설의 빵집 정복자', 빵집 50곳) | 재계산 (도감 발견 수 = 내가 리뷰를 남긴 서로 다른 빵집 수) |
| **결정** | **모든 배지를 현재 조건으로 재계산**해요. 리뷰를 지워서 조건을 못 채우면 배지도 회수돼요(영구 기념 배지 없음) |

## 4. 접근 권한 요약 (RLS)

| 대상 | 비로그인 | 로그인 · **이메일 미인증** | 로그인 · 인증 완료 |
|---|---|---|---|
| 프로필 · 리뷰 · 게시글 · 댓글 · 좋아요 · 빵집 | 읽기 | 읽기 | 읽기 |
| 리뷰 · 글 · 댓글 · 좋아요 · 방문 쓰기 | ❌ | ❌ (`EMAIL_NOT_VERIFIED`) | **내 것만** 작성, 리뷰·글은 내 것만 수정, 모두 내 것만 삭제 |
| 방문 체크 읽기 | ❌ | 내 것만 | 내 것만 |
| 닉네임 변경 | ❌ | ❌ | 내 것만 |
| 빵집 등록 | ❌ | ❌ | ❌ (서버 비밀 키를 가진 Edge Function만) |

> 이메일 인증을 켜면 미인증 사용자는 애초에 로그인 세션이 안 생기지만, **DB에서도 한 번 더** `is_email_verified()`로 막아 두었어요(이중 방어).
> 공개 읽기 테이블에는 이메일 등 개인 정보가 없어요(이메일은 `auth.users`에만 있고 노출되지 않음).

## 5. 이메일 인증 (정책 2번)

- 대시보드 Authentication → **Confirm email 켜기**. 가입하면 인증 메일 → 링크 클릭 후 로그인 가능
- 화면에서 제공: ① 가입 직후 "메일을 보냈어요" 안내 ② **재발송**(`auth.resend`) + 연타 방지 쿨다운 ③ 오류 한글화 (미인증 로그인 `email_not_confirmed`, 잘못된 비밀번호, 이미 가입된 이메일, 메일 발송 한도 `over_email_send_rate_limit`)
- ⚠️ **기본 메일 서버는 시간당 발송 수가 아주 적어서 실사용이 어려워요.** 인증을 필수로 했으므로 **커스텀 SMTP 설정이 3단계 전에 필요**해요 (예: Resend, Brevo 등 무료 구간이 있는 서비스. 발신 도메인 인증이 필요한 서비스도 있어요). 어떤 서비스를 쓸지는 결정이 필요해요.
- HashRouter와 메일 링크 충돌 방지: **PKCE 방식**으로 설정하고 Redirect URL을 등록해요(로컬 · GitHub Pages · Vercel).

## 6. 유효한 빵집 등록 방식 (정책 3번의 핵심)

카카오 장소는 브라우저에서만 검색하고 있어서, DB에는 "유효한 빵집" 목록이 필요해요.

1. 사용자가 처음 리뷰/방문 체크를 하는 빵집이 `bakeries`에 없으면, 앱이 Edge Function **`register-bakery`**를 호출 `{ id, name, x, y }`
2. 함수가 **카카오 로컬 REST API**(이름 + 좌표 반경 검색)로 같은 `id`가 실제로 있는지, 카테고리가 제과·베이커리인지 확인
3. 확인되면 서버 비밀 키로 `bakeries`에 upsert (지역 `district_id`는 좌표로 가장 가까운 5개 지역 중 결정, 또는 앱이 보낸 값 검증)
4. 이후 리뷰는 외래키로 보호돼요. 카카오 REST 키는 **함수 비밀값**에만 두고 프런트에는 두지 않아요.
- 대안(더 단순): 관리자가 약 75곳을 한 번에 시드. 하지만 새 빵집이 늘 때마다 수동 작업이라 함수 방식을 추천해요.
- 한계: 함수를 남용해 임의 장소를 등록하려는 시도는 **카카오 검증 + 요청 속도 제한**으로 막아요(6단계 이전 4단계 작업).

## 7. 예시 데이터 분리 (정책 4번)

- **운영 DB에는 예시 리뷰 · 게시글 · 랭킹 · 가짜 계정을 만들지 않아요.** 예시 빵집(숫자 ID)은 `bakeries`에 없으므로 EXP 대상이 될 수 없어요.
- 실제 랭킹(`leaderboard` 뷰)은 DB 데이터만 집계 → 예시가 섞일 수 없어요.
- 데모가 필요하면 **`VITE_DEMO_MODE=true`일 때만** 프런트 상수 데이터를 "데모 데이터" 배너/표시와 함께 보여줘요(DB에는 쓰지 않음). 기본값은 꺼짐.
- 실제 데이터가 없으면 빈 상태 화면(지금 랭킹에 이미 있는 방식)을 보여줘요.

## 8. 키 · 환경변수 · 리전 · 무료 플랜

| 항목 | 내용 |
|---|---|
| 프런트 키 | Supabase가 기존 `anon` 키를 **publishable 키(`sb_publishable_…`)** 로 대체 중이에요(출처: [공식 가이드](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys)). `.env`에 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` 사용 |
| 비밀 키 | `sb_secret_…`(구 service_role)는 **Edge Function 서버 쪽에서만**. 프런트 · git · 대화에 넣지 않아요 |
| 리전 | Supabase에 서울(`ap-northeast-2`)이 있는 것으로 알고 있지만 **검색으로 확인하지 못했어요**. 프로젝트 생성 화면의 리전 목록에서 서울을 고르고, 없으면 가까운 **도쿄**를 추천해요 |
| 일시정지 | 무료 플랜은 **7일간 활동이 매우 적으면 자동 일시정지**, 정지 후 **90일 안에** 대시보드에서 복구 가능([공식 문서](https://supabase.com/docs/guides/platform/free-project-pausing)) |
| keep-alive | **만들지 않아요**(요청하신 대로). 방치되면 정지될 수 있다는 점을 운영 중 감수하고, 안내 문구로 대응 |
| 백업 | 무료 플랜은 자동 백업 **없음**(자료 기준 · [요금표](https://supabase.com/pricing.md)에는 Pro부터 일일 백업 7일 보관). 월 1~2회 수동 내보내기(`pg_dump` 또는 대시보드 CSV) 절차를 7단계에서 문서화 |
| 한도 | DB 500MB · 사용자 5만 MAU · 저장소/전송량은 자료마다 수치가 달라 가입 후 **대시보드에서 확인** |

## 9. 백엔드 전환 · 롤백 안전장치 (정책 9번) — 3단계부터 적용

- `VITE_DATA_BACKEND=local|supabase`. 기본은 `local`(지금과 동일).
- **모드가 한눈에 보이게**: Supabase 모드에는 "계정에 저장됨", 로컬 모드에는 "이 브라우저에만 저장" 안내를 계속 표시
- **조용한 폴백 금지**: Supabase 모드에서 네트워크/권한 오류가 나면 **실패를 그대로 화면에 표시**하고, 로컬에 몰래 저장하지 않아요(저장소 계층이 `RepositoryError`를 던지는 지금 구조 유지)
- 기존 localStorage는 **읽기만** 하고 지우지 않아요. 전환 전 **JSON 백업 내려받기** 제공, 이전은 별도 화면(4단계)에서 사용자가 직접
- 로컬 리뷰는 EXP 규칙이 달라요(예시 빵집·상한 없음) → 이전 시 **유효한 빵집(카카오 ID)만** 올라가고, 예시 빵집 리뷰와 하루 상한 초과분은 "이전되지 않음"으로 안내

## 10. 앱 코드에 생기는 변경 (4단계 이후 반영)

| 현재 | Supabase 모드 |
|---|---|
| EXP를 클라이언트가 모든 리뷰로 계산 | **서버 뷰 `user_progress`의 EXP/레벨을 표시**(내 상태창도 서버 값). 클라이언트 계산은 저장 전 "예상 EXP" 미리보기 용도로만 |
| 예시 빵집(숫자 ID) 리뷰도 EXP | EXP 없음(예시 빵집은 DB에 없음) — 화면에 "EXP 대상이 아니에요" 표시 |
| 수정 시 사진을 붙이면 EXP +10 | 작성 때 있었던 사진만. 수정 미리보기 문구 변경 |
| 하루 상한 없음 | 하루 100 EXP를 채우면 "오늘의 EXP 한도를 채웠어요" 안내(저장은 됨) |
| 댓글 수정 가능(화면 내 임시) | **댓글 수정 제거**(정책: 작성·조회·삭제) |
| 임시 닉네임 로그인 | 이메일·비밀번호·닉네임 가입, 인증 안내/재발송 |

| 유지 | 기존 RPG 디자인, 카카오 지도, 로컬 데이터는 그대로 |
| 민감 정보 | `.env`, 비밀번호, 비밀 키는 커밋하지 않음 |
| Supabase 프로젝트 | 사용자가 직접 생성·설정 |

아직 정해지지 않은 것: **SMTP 서비스**(인증 메일 발송용, `docs/supabase-setup-guide.md` 3-2 참고)

## 12. 이후 순서

2단계 프로젝트 생성·환경변수 안내(여기서 사용자 작업 필요) → 3단계 가입·로그인 → 4단계 프로필·리뷰·EXP·배지 연동(+`register-bakery`) → 5단계 도감·방문 체크 → 6단계 커뮤니티 → 7단계 랭킹 → 8단계 전체·모바일 테스트. **각 단계 끝에 보고하고 승인 후 다음 단계로 가요.**
