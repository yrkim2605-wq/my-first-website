## 1. "최대 30일"과 "삭제가 며칠 늦어질 수 있음"의 충돌 — 운영 방식으로 해결

**충돌의 원인:** 지금 설계는 매일 28일 넘은 백업을 직접 삭제하고 GitHub 자동 만료(30일)를 보조로 둬요. 이러면 삭제 지연이 생길 때 곧바로 30일을 넘길 수 있어서 "며칠 늦어질 수 있어요"를 써야 했어요. 문구를 얼버무리는 대신 **운영에 여유를 둬서** 30일 약속이 실제로 지켜지게 하는 쪽이 맞아요.

**제안: 내부 기준을 30일보다 훨씬 짧게 잡아요 (여유 9일).**

| | 지금 초안 | 제안 |
|---|---|---|
| 직접 삭제 작업(`cleanup-backups`) 기준 | 28일 초과 | **21일 초과** (매일 확인) |
| GitHub 자동 만료(`retention-days`) | 30일 | **25일** (직접 삭제가 실패할 때의 두 번째 장치) |
| 삭제가 늦어져도 30일을 넘기지 않는 여유 | 2일 | **9일** (직접 삭제 기준), 5일 (자동 만료 기준) |
| 동시에 보관되는 사본 수(매일 백업) | 최대 28개 | 최대 21개 (저장 용량 부담도 줄어요) |

**이렇게 하면 방침의 약속을 이렇게 쓸 수 있어요:** "만든 날부터 21일이 지나면 삭제하고, 삭제 작업이 실패하더라도 30일 안에는 지워지도록 이중으로 설정해 뒀어요."

**여전히 보장할 수 없는 것 (정직하게):**
- GitHub가 API로 삭제한 Artifact를 **내부 저장소에서 물리적으로 언제 지우는지**는 공식 문서에 없어요. 문서는 "삭제하면 복구할 수 없다(cannot be restored)"까지만 말해요. → 방침은 "삭제해요 / 되살릴 수 없어요"까지만 말하고, GitHub 내부 처리는 5장에서 "GitHub 정책을 따라요"라고 분리해서 적어요.
- 두 장치가 동시에 9일 넘게 실패하고 점검도 놓치면 30일을 넘길 수 있어요 → 실패 알림 메일 + 주 1회 점검(README 7장)으로 막아요.

**사전 검증(첫 실행 때):** `cleanup-backups`를 dry-run으로 한 번 돌려 삭제 대상이 맞게 잡히는지 보고, 실제 삭제 후 Artifact 목록에서 사라지는지, 다운로드가 막히는지 확인해요 (목록/다운로드에서 사라지는 것은 직접 확인할 수 있어요).

> 승인되면 `backup-db.yml.draft`의 `retention-days: 25`, `cleanup-backups.yml.draft`의 `MAX_AGE_DAYS: '21'`로 바꿔요 (지금은 28 / 30 그대로예요).

## 2. 사진 파일 삭제 — "탈퇴 즉시 완전 삭제"라고 단정하지 않는 근거와 문구

**실제 삭제 방식 (코드 `supabase/functions/delete-account/index.ts`):**
1. 탈퇴 요청 → **사진을 먼저** 삭제해요: 내 폴더(`{user_id}/…`, 하위 폴더 포함)의 파일을 모두 찾아 Storage API로 삭제 요청해요.
2. 일부만 지워지거나 오류가 나면 **계정은 그대로 두고 실패**로 끝나요 (다시 시도 가능).
3. 사진 삭제가 끝난 뒤에야 계정을 삭제해요 → 리뷰 · 글 · 댓글 · 좋아요 · 체크가 연쇄로 삭제돼요.

**단정하면 안 되는 이유:**
- Supabase 문서: 파일을 지우면 CDN 캐시가 자동으로 무효화되지만 전파에 **최대 약 60초**가 걸려요. 브라우저 캐시는 무효화되지 않고 기본 **약 1시간** 남을 수 있어요.
- 공개 버킷이라 사진 주소를 아는 사람이 이미 저장하거나 복사한 사본은 지울 수 없어요.
- Supabase 인프라 내부(저장소 제공업체 쪽)에서 파일이 물리적으로 지워지는 방식은 확인하지 못했어요. 사진은 DB 백업에 들어가지 않아요(Supabase 문서).

**문구 원칙:** "삭제 요청을 처리하며, 처리가 끝나야 탈퇴가 완료돼요" + "캐시로 짧은 시간 보일 수 있어요" + "다른 사람이 이미 저장한 사본은 지울 수 없어요". "즉시", "완전히", "흔적 없이" 같은 표현은 쓰지 않아요.

## 3. GitHub에 암호화된 백업을 보관할 때 추가 고지가 필요한가

**결론: 필요하다고 보고 쓰는 것이 안전해요 (법률 검토 필요).**
- 해설 자료에 따르면 국외 이전(제28조의8)은 ① 별도 동의 또는 ② **계약 이행을 위해 처리위탁 · 보관이 필요한 경우 처리방침에 공개** 등의 근거가 있어야 해요. 백업 보관은 ②에 해당할 여지가 크지만, 그러려면 아래 항목이 처리방침에 있어야 한다고 설명돼요 (원문 확인 필요).
- 암호화돼 있어서 GitHub가 내용을 읽을 수 없더라도, "개인정보를 국외 서버에 보관"하는 것이므로 **보수적으로 위탁 · 국외 이전으로 보고 고지**하는 편이 안전해요.

**공개해야 한다고 알려진 항목과 우리 현황**

| 항목 | 우리 현황 |
|---|---|
| 이전되는 개인정보 항목 | 백업에 담기는 항목: 이메일 · 닉네임 · 비밀번호(암호화된 값) · 가입 시 동의 기록 · 일지 · 글 · 댓글 · 좋아요 · 체크 · 신고 (사진 제외) |
| 이전되는 국가 · 시기 · 방법 | **미확인.** GitHub는 Artifact 저장 국가를 공개하지 않아요 (미국 등으로 추정, 확정 못 함). 시기: 매일, 방법: 암호화 후 네트워크 전송 |
| 이전받는 자(법인명 · 연락처) | GitHub, Inc.(Microsoft 계열)로 보이지만 **정확한 법인명 · 연락처는 확인 필요** |
| 이용 목적 · 보유 기간 | 목적: 장애 · 사고 시 복구. 보유 기간: 백업 보관 기간과 같음 (위 1장) |
| 이전 거부 방법과 효과 | 정해야 해요. 예: 문의 메일로 거부 요청 → 서비스 이용이 제한될 수 있음 (필수 백업이라 개별 제외가 어려워요) |

**이번 변경과 별개로 보이는 빈틈:** 지금 방침의 국외 이전 문구는 "일부는 해외에 서버가 있을 수 있어요" 수준이에요. Supabase(운영사), Brevo, GitHub Pages 모두 위 항목(법인명 · 국가 · 항목 · 거부 방법)이 구체적으로 적혀 있지 않아요. 백업이 아니더라도 **공개 전 법률 검토에서 반드시 짚을 항목**이에요.

**대안 (결정 필요):**
| 선택 | 장점 | 단점 |
|---|---|---|
| GitHub 비공개 저장소 + 위 항목 고지 (현재 안) | 무료 · 자동화 쉬움 | 국가를 확정해서 쓸 수 없음 |
| 별도 Supabase 프로젝트(서울)에 암호화 백업 보관 | 저장 지역(서울)을 확정해서 쓸 수 있음 | 운영사는 같은 해외 법인, 프로젝트 하나 더 관리, 무료 한도 |
| 내 PC/외장 디스크에 보관 | 국외 이전 없음 | PC가 꺼지면 백업이 빠짐, 자동 삭제 보장 약함 |
