# 관문 C 실행 계획: 가짜 데이터 복구 시험 (승인 대기 — 아직 아무것도 실행하지 않았어요)

> 작성: 2026-10-15. 선행: 관문 A(`initdb`), 관문 B(서버 시작 · 바인딩 · 외부 차단 · 빈 `bakery_rehearsal` · 정상 종료) 완료 — `rehearsal-log.md` 3~4단계.
> 이 문서는 **계획**이에요. 실제 Supabase에는 접속하지 않고, 가짜 데이터(`…@example.invalid`)만 써요. 실행은 사용자 승인 뒤에 해요.

## 0. 이 시험이 확인하려는 것 / 확인하지 못하는 것

| 확인하려는 것 | 이유 |
|---|---|
| (1) 워크플로의 **정확한 명령**(`pg_dump` 두 번 + `tar` + `age` 2인) 으로 만든 백업이 **복호화 · 복원**되는지 | README 8-1 |
| (2) 복원 후 **행 수 · 외래키 · 비밀번호 해시 · `raw_user_meta_data`(약관 동의 기록 포함)** 가 원본과 같은지 | 계정 복구 가능성(README 2장) |
| (3) **`pg_dump --schema=public`에 빠지는 것들**이 실제로 무엇인지: `auth.users`에 걸린 프로필 자동 생성 트리거, `storage.objects` 정책 · 버킷 행, `GRANT`(`--no-privileges`) | 코드를 읽고 세운 가설(아래 2장), 빠지면 복구 절차에 "재적용" 단계가 필요 |
| (4) 프로필 **트리거 충돌**이 실제로 생기는지, "계정 먼저 → 마이그레이션 나중" 순서가 충돌을 없애는지 | `reconfirm-pending-design.md` 4장 |
| (5) **상황 A**: "운영 DB에 살아 있는 계정만 가져오기"가 **가짜 탈퇴자를 걸러내는지** | README 9장 |
| (6) **상황 B**(격리 `quarantine` 방식) 프로토타입이 PostgreSQL 안에서 되는지: 외부 역할(`anon`/`authenticated`) 접근 거부, 본인 확인 시 이동, 정리 | 설계 검증 (구현 아님) |

| 확인하지 못하는 것 (시험용 Supabase 프로젝트 · 가짜 계정이 따로 필요) |
|---|
| 복원된 계정의 **실제 로그인**(GoTrue), `banned_until`, 밴 상태의 재설정 메일, Data API가 `quarantine`을 노출하지 않는지, 실제 Storage 정책 동작, Edge Function 동작, Supabase의 실제 기본 권한 · `supabase_admin` 소유 객체, 서버 버전 차이 |

## 1. 진행 단계와 승인 지점

| 단계 | 내용 | 서버 | 승인 |
|---|---|---|---|
| **C-prep** | 시험용 SQL · 실행 스크립트를 **파일로 작성**해서 사용자가 읽고 검토 (실행 없음) | 꺼져 있음 | 이 문서 승인 후 진행 |
| **C-run** | 아래 3장 순서로 실행. `try/finally`로 마지막에 항상 `pg_ctl stop -m fast -w` | 시작 → 종료 | 파일 검토 후 **별도 승인** |
| **C-report** | 결과 · 시스템 변경 · 발견한 문제 · 문서 갱신안 보고 | 꺼져 있음 | — |

C-prep에서 만들 파일 (모두 `docs/backup/rehearsal/`, 가짜 값만 들어 있어 Git에 올려도 안전): `00-auth-stub.sql`, `10-fake-seed.sql`, `20-compare.sql`, `gateC.ps1`(실행기), `README.md`(읽는 법).

## 2. 코드에서 미리 알아낸 가설 (시험으로 확인해요)

| 가설 | 근거 | 시험에서 볼 것 |
|---|---|---|
| `pg_dump --schema=public`은 **`auth.users`의 트리거 `on_auth_user_created`를 담지 않는다** (트리거는 `auth.users` 소속) | `0001_schema.sql`이 `create trigger … on auth.users`로 만들어요 | 복원 DB에 트리거가 있는가 → 없으면 `0001`의 트리거 문장만 재적용하는 단계 필요 |
| `storage.objects`의 **정책 · 버킷 `photos` 행**도 `public` 덤프에 없다 | `0003`/`0008`/`0010`이 `storage` 스키마를 건드려요 | 복원 DB의 `storage` 정책 수가 원본과 같은가 (스텁에서) |
| `--no-privileges`라서 **`GRANT`가 복원되지 않는다** | `0007`이 `service_role` 권한을 직접 부여, 2026년부터 새 표는 자동 노출되지 않음 | 원본 ↔ 복원본의 표 권한(`information_schema.role_table_grants`) 비교. 다르면 "권한 포함 덤프" 또는 "권한 재적용" 필요 |
| 가입 시 닉네임이 없거나 형식이 틀리면 **사용자 추가가 통째로 실패**한다 | `handle_new_user()` + `profiles` 검사 | 계정을 먼저 복원할 때 트리거가 있으면 충돌 · 실패하는가 |

## 3. C-run 순서 (모든 DB는 같은 로컬 서버 안: `bakery_rehearsal`(원본 역할), `bakery_stage`, `bakery_restore_r1~r4`)

| # | 작업 | 확인할 것 |
|---|---|---|
| C0 | 사전 점검 · 시작 전 스냅샷 · 서버 시작(관문 B와 같은 방식) · 리스닝 `127.0.0.1:54329`만, 외부 차단 재확인 | 관문 B와 동일 |
| C1 | 원본 준비: `00-auth-stub.sql`(실제 모양에 가깝게 늘린 가짜 `auth`: `users` 주요 칸 · `identities`(생성 칸 `email` 포함) · 시험용 `sessions`/`refresh_tokens`/`audit_log_entries`, `auth.uid()`, 역할 3개) + `storage` 스텁 + `supabase/migrations/0001~0010` | 마이그레이션 10개가 일반 PostgreSQL 17.11에서 오류 없이 적용되는가 |
| C2 | 가짜 데이터 `10-fake-seed.sql`: 사용자 5명 + **백업 이후 탈퇴할 가짜 사용자 1명**(`fake-withdrawn@example.invalid`), 가짜 해시 문자열(`FAKE_HASH_…`, 실제 비밀번호 아님), 약관 동의 기록 `terms_version`, 일지 · 글 · 댓글 · 좋아요 · 방문 · 신고 · 운영자 1명 | 트리거로 프로필이 자동 생성되는가, 닉네임 규칙 통과 |
| C3 | 기준값 저장: 표별 행 수, `auth.users` 해시 · 메타데이터 `md5`, 권한 · 정책 · 트리거 · 함수 · 보기 목록 | — |
| C4 | **백업(워크플로와 같은 명령):** `pg_dump -Fc --no-owner --no-privileges --schema=public` + `pg_dump -Fc --no-owner --no-privileges --data-only --table=auth.users --table=auth.identities` → `pg_restore --list` 검사(`public` 항목 > 20, 계정 덤프의 `TABLE DATA` 정확히 2) → `tar` → `age -r 키1 -r 키2` | 두 덤프에 세션 · 토큰 · 감사 로그 표가 **없는가**, 암호문에 평문이 없는가 |

| C6 | **원본에서 "백업 이후" 변화 흉내:** 가짜 탈퇴자를 원본에서 삭제(연쇄 삭제), 백업 이후 신규 가입자 1명 추가 | — |
| C7-R1 | **워크플로 그대로 복원(빈 새 DB):** 계정 데이터 → `public` 덤프 | 오류 목록, 행 수 · 해시 · 메타데이터 일치, 빠진 객체(가설 3개) 실제 확인 |
| C7-R2 | **순서를 바꾼 충돌 시험:** 마이그레이션을 먼저 적용한 DB에 계정 복원 | 프로필이 자동 생성되며 데이터 복원과 충돌하는가 (README의 설명이 맞는지) |

| C8 | 정리: 서버 정상 종료 → 프로세스 · 포트 · `postmaster.pid` · 시스템 변경 비교 | 관문 B와 동일 |
| C9 | 결과 정리: 합격 기준 표 · 발견한 문제 · README/설계 문서 수정안 | — |

## 4. 합격 기준 (각 항목을 결과 보고에 ✅/❌ 로 표시)

- [ ] 마이그레이션 10개가 오류 없이 적용됨
- [ ] 워크플로 명령 그대로 만든 두 덤프가 `pg_restore --list`로 읽힘 (`TABLE DATA` 2개, 세션 · 토큰 표 없음)
- [ ] 키1/키2 각각으로 복호화되고 원본 `tar`와 해시 동일, 무관한 키는 거부
- [ ] R1: 표별 행 수 일치, `auth.users`의 해시 · 메타데이터 일치, 외래키 오류 없음 (또는 오류 목록을 정확히 기록)
- [ ] R1: 빠진 객체(트리거 · `storage` 정책 · `GRANT`)가 **실제로** 무엇인지 목록화
- [ ] R2: 트리거 충돌이 재현되는지 / 안 되는지 기록
- [ ] R3: 가짜 탈퇴자가 복원 대상에서 제외됨
- [ ] R4: 외부 역할의 `quarantine` 접근 거부, 확인 시 이동 성공, 정리 후 잔여 0
- [ ] 서버 정상 종료, 프로세스 · 포트 해제, 시스템 변경 없음 (`C:\bakery-secure\pg` 안 파일 제외)
- [ ] 비밀번호 · 실제 개인정보가 로그 · 문서 · Git에 없음

**하나라도 ❌이면 "복구 가능"이라고 쓰지 않고, 실패 원인과 필요한 절차 변경을 문서에 기록해요.**

## 5. 예상 파일 · 시스템 변경과 중단 조건

| 항목 | 내용 |
|---|---|
| 새 파일 | `pg\rehearsal-files\`(덤프 · 암호문 · 복호화 파일 · tar, 가짜 데이터), `pg\rehearsal-keys\`(임시 age 키 3개, 시험 후 삭제), 로그, 스냅샷. 모두 `C:\bakery-secure\pg` 안 |
| DB | 같은 로컬 서버 안 데이터베이스 약 6개(시험 후 삭제할 수 있음), 역할 3개(`anon`/`authenticated`/`service_role`, 이 서버 클러스터 안 가짜 역할) |
| 시스템 변경 | 없을 것으로 예상 (관문 B와 같은 방식). 서비스 · 레지스트리 · 계정 · 방화벽 · PATH 변경 없음 |
| 중단 조건 | 관문 B의 조건 전부(UAC · 관리자 요구, 방화벽 창, 리스닝 주소가 `127.0.0.1:54329` 이외, 외부 연결 성공, 응답 없음) + **Supabase 또는 외부 호스트로 접속하려는 징후**, `C:\bakery-secure\pg` 밖에 파일이 생기려는 징후. 어떤 경우든 추가 작업 없이 서버 종료 후 보고 |
| 임시 키 | `age-keygen`의 "world-readable" 경고는 Windows에서 항상 나는 오탐(README 4장). 안전 확인은 `icacls`. 운영 키가 **아니에요** |
| 정리 | 시험 후 복호화 파일 · 임시 키는 삭제를 권해요(가짜 데이터지만 습관대로). 실행기가 삭제 목록을 보여주고, 삭제는 승인 후에 해요 |

## 6. 정직하게 남는 한계
- 같은 클러스터 안의 데이터베이스끼리 복원하므로 **새 Supabase 프로젝트로 옮길 때의 차이**(역할 · 확장 · 기본 권한 · 소유자)는 재현하지 못해요. 이 시험은 "데이터와 객체가 덤프에 들어 있고 순서대로 복원되는가"에 한정돼요.
- 로케일 `C`와 서버 17.11은 Supabase 프로젝트와 다를 수 있어요.
- 이 시험이 통과해도 "계정까지 완전히 복구된다"고 쓰지 않아요. 로그인은 8-2(시험용 Supabase + 가짜 계정)에서 따로 확인해야 해요.
