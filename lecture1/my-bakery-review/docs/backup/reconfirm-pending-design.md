# 탈퇴 계정 "재확인 대기" 기능 설계 (설계만 — 구현하지 않았어요)

> 상태: **설계 문서.** 구현 여부는 가짜 데이터 복구 시험(README 8-1) 결과를 본 뒤 사용자가 결정해요.
> 대상 상황: README 9장 **상황 B** (운영 `auth`와 `public`을 둘 다 잃어서 "지금 누가 회원인지" 알 수 없는 복원).
> 요구: 단순히 화면에서 숨기는 것이 아니라 **로그인 · API 접근 · 데이터 조회까지** 막을 것.

## 1. 풀려는 문제와 목표

백업을 새 프로젝트에 복원하면, 백업 시점 이후에 탈퇴한 사람의 계정 · 일지 · 글이 되살아나요. 누가 탈퇴했는지는 어디에도 없어요(탈퇴 장부는 도입하지 않기로 했어요).

| 목표 | 설명 |
|---|---|
| G1. 노출 차단 | 본인이 다시 확인하기 전까지, **다른 사람은 어떤 경로로도** 그 사용자의 데이터를 볼 수 없다 (화면 · API · 랭킹 · 검색 · 집계 모두) |
| G2. 접근 차단 | 확인 전의 계정은 **글 쓰기 · 사진 올리기 · 신고 · 좋아요 등 모든 쓰기**를 할 수 없다 |
| G3. 연락 금지 | 복원된 계정에 우리가 먼저 메일을 보내지 않는다 |
| G4. 자동 정리 | 정해둔 기간 안에 확인하지 않은 계정은 삭제한다 (탈퇴자는 확인하지 않으므로 사라진다) |
| G5. 본인 선택 | 확인 화면에서 "계속 이용" 또는 "탈퇴" 중 고를 수 있다 |

## 2. 두 가지 설계 비교

### 안 1. 플래그 방식 (`profiles.restore_pending_at` + 모든 규칙에 조건 추가)
- 데이터는 `public`에 그대로 두고, 대기 계정이면 보지 못하게 **모든 읽기 규칙(RLS) · 보기(view) · 함수 · Edge Function**에 조건을 넣어요.
- 문제: 고쳐야 할 곳이 많고(표 8개 + 보기 9개 + 보안 정의자 함수 + Edge Function 2개 + Storage 규칙), **하나라도 빠지면 그 경로로 노출돼요.** 앞으로 새 표 · 보기를 추가할 때마다 같은 실수 위험이 생겨요. "기본은 보임, 막는 규칙을 더함" 구조라서 안전하지 않아요.

### 안 2. 격리 스키마 방식 (권장)
- 복원할 때 사용자 소유 데이터를 `public`이 아니라 **비공개 스키마 `quarantine`** 에 넣어요. 본인이 확인하면 **그 사용자의 행만** `public`으로 옮겨요.
- "기본은 없음, 확인 때만 생김" 구조라서 **빠뜨린 경로가 있어도 보여줄 데이터가 `public`에 없어요.** 고칠 곳도 훨씬 적어요.
- 단점: 복구 도구(이동 · 정리 함수)와 확인 화면이 필요해요. 닉네임 충돌 처리가 필요해요.

→ **안 2를 권장해요.** 이하는 안 2 기준이에요.

## 3. 어떤 데이터가 어디로 가나

| 구분 | 표 | 복원 위치 |
|---|---|---|
| 사용자 소유 | `profiles`, `reviews`, `posts`, `comments`, `post_likes`, `bakery_visits`, `reports` | **`quarantine` 스키마** (확인 때 `public`으로 이동) |
| 공용 데이터 | `bakeries`, `game_settings` | `public`에 바로 복원 (개인정보 아님) |
| 운영자 목록 | `admins` | 자동 복원하지 않음. 운영자 계정이 확인된 뒤 **수동 등록** |
| 계정 | `auth.users`, `auth.identities` | 새 프로젝트의 `auth`에 복원 (아래 4장 순서) |
| 사진 파일 | (백업에 없음) | 복원 안 됨 — 확인 때 사진 연결 정보도 비어 있음 |

## 4. 복원 순서 (새 프로젝트, 가짜 시험에서 먼저 확인)

1. 새 Supabase 프로젝트를 만든다. 사이트는 점검 안내 상태로 둔다 (정적 사이트라 가능).
2. `auth.users` · `auth.identities` 데이터를 먼저 복원한다. **이때 프로필 자동 생성 트리거(`on_auth_user_created`)가 아직 없어야 해요** → 복원 후에 마이그레이션을 적용해서 트리거가 나중에 생기게 해요 (이미 들어온 사용자에게는 발동하지 않아요). 이렇게 하면 프로필 자동 생성 충돌이 사라져요.
3. 스테이징 DB에 `public` 덤프를 복원하고, 사용자 소유 표를 `quarantine`으로 옮긴다 (`ALTER TABLE … SET SCHEMA quarantine`, 메타데이터 변경이라 빨라요). 이 스키마를 덤프해서 새 프로젝트에 로드한다.
4. 새 프로젝트에 `supabase/migrations`를 적용해 빈 `public`을 만든다. 공용 데이터를 `public`에 넣는다.
5. `quarantine` 권한을 닫는다: `anon` · `authenticated` · `service_role`에서 모든 권한 회수, **Data API의 노출 스키마에 추가하지 않는다** (대시보드 설정에서 직접 확인).
6. 서비스를 열기 전 점검 쿼리: `public`에 사용자 소유 행이 0개인지, `quarantine` 행 수가 백업과 같은지, 외부 역할이 `quarantine`을 읽을 수 없는지.

## 5. 본인 확인 흐름

```
로그인(이메일 · 비밀번호, 기존 해시 보존) 
  → 앱이 확인: public.restore_status()  
      ├ 'active'  → 평소처럼 사용
      └ 'pending' → "복구 확인" 화면
            ├ [계속 이용할게요] → public.confirm_restore() → 내 행만 quarantine → public 이동 → 평소 화면
            └ [탈퇴할게요]     → 기존 탈퇴 흐름(delete-account) → 계정과 quarantine 행 삭제
```

- `confirm_restore()`: 보안 정의자 함수. **`auth.uid()`의 행만** 옮기고, 한 트랜잭션에서 처리해요. 순서는 `profiles` → 나머지. 복원 후 새로 가입한 다른 사람이 같은 닉네임을 쓰고 있으면 닉네임 변경을 요구해요 (유일 인덱스 때문).
- `restore_status()`: `auth.uid()`가 `quarantine.profiles`에 있고 `public.profiles`에는 없으면 `'pending'`. 그 밖에는 `'active'`.
- 확인 화면 문구 초안: "서비스 복구 작업이 있었어요. 계속 이용하시려면 아래 버튼을 눌러 주세요. 탈퇴하셨던 분이라면 [탈퇴할게요]를 눌러 정보를 지워 주세요. (복구 후 25일 안에 확인하지 않으면 계정이 삭제돼요.)"

## 6. 경로별 차단 방식 (G1 · G2)

| 경로 | 평소 | 대기 계정 | 이유 · 방법 |
|---|---|---|---|
| **로그인(인증)** | 가능 | **기본 안: 허용** / **강화 안: 차단** (아래 6-1) | 확인 화면에 도달하려면 로그인이 필요해요. 로그인 토큰으로 할 수 있는 일은 아래 표처럼 매우 좁아요 |
| **REST API(PostgREST) 읽기** | RLS | **조회 결과 0건** | 대기 계정의 행은 `public`에 없고, `quarantine`은 노출 스키마가 아니에요 |
| **REST API 쓰기** | RLS | **거부** | `profiles` 행이 없어서 외래키 · 정책에서 막혀요. 추가로 쓰기 정책에 "내 프로필이 있음" 조건을 넣는 것을 검토 (구현 시 확정) |
| **RPC(함수)** | 일부 허용 | **`restore_status`, `confirm_restore`만** | 보안 정의자 함수 목록을 모두 점검(`is_email_verified`, `is_nickname_available`, `handle_new_user`, 운영자 처리 함수 등). 새 함수는 `auth.uid()`가 활성 회원인지 먼저 확인 |
| **보기 · 랭킹 · 집계** | `public` 표에서 계산 | **반영 안 됨** | 원본 표(`public`)에 행이 없어서 `user_stats`, `ranking_*`, `post_feed`, `comment_feed`에 안 나와요 |
| **Edge Function `register-bakery`** | 로그인 사용자 허용 | **거부 필요 (수정 대상)** | 서비스 권한으로 동작해서 RLS를 건너뛰어요 → 프로필이 없는 사용자는 거부하는 검사를 넣어야 해요 |
| **Edge Function `delete-account`** | 허용 | **허용 (수정 대상)** | 대기 계정도 탈퇴할 수 있어야 해요 + `quarantine` 행도 함께 삭제. 프로필이 없어도 동작하는지 확인 필요 |
| **Storage(사진 올리기)** | 이메일 인증 사용자 + 내 폴더 | **막아야 함 (수정 대상)** | 현재 정책은 인증 여부와 폴더 이름만 봐요. "활성 회원" 조건을 정책에 추가해요. 사진 읽기는 공개 버킷이라 정책으로 막을 수 없는데, **복원본에는 사진 파일이 없어요** |
| **Realtime / GraphQL** | (사용 여부 확인 필요) | 노출 스키마 설정에 따름 | 앱이 쓰는지 점검. `quarantine`은 노출하지 않으니 해당 없음 |
| **관리자 화면 · 신고** | 운영자만 | 해당 없음 | `admins`는 수동 복원. `reports`는 `quarantine`에 두고 운영자가 필요 시 따로 확인 |
| **메일(인증 · 재설정)** | 정상 | **위험 있음 (6-2)** | 제3자가 탈퇴자 주소로 재설정 메일을 유발할 수 있어요 |

### 6-1. 로그인 차단 수준 선택 (결정 필요)
- **기본 안 (권장): 로그인 허용 + 데이터 격리.** 대기 계정이 로그인해도 볼 수 있는 것도, 할 수 있는 것도 없어요(확인 화면 · 탈퇴만). 실제 노출 위험은 데이터 격리로 이미 막혀 있어요.
- **강화 안:** 복원 직후 모든 복원 계정의 `auth.users.banned_until`을 먼저 무기한으로 설정해서 **로그인 자체를 막고**, 본인이 문의 메일(가입한 이메일에서 보낸 것)로 요청하면 운영자가 해제해요. 회원이 적은 베타에서는 가능하지만 운영자가 일일이 처리해야 하고 이용자가 불편해요. 위급할 때 켜는 **비상 스위치**로 문서화해 둬요.
- 어느 쪽이든 **밴 상태에서도 기존 JWT가 만료 전까지 유효**하다는 점(새 프로젝트로 복원하면 이전 토큰은 서명 키가 달라 무효)과 **밴 상태의 재설정 메일 동작은 아직 확인하지 못했어요** → 시험용 Supabase 프로젝트에서 가짜 계정으로 확인해야 해요.

### 6-2. 메일 위험
- 누군가 탈퇴자의 이메일 주소로 "비밀번호 재설정"을 요청하면 그 사람에게 메일이 가요. 우리가 먼저 보내는 것은 아니지만 **연락이 가는 건 같아요.**
- 완화책: ① 복원 직후 첫 기간에 사이트에 안내 ② (가능하면) 대기 계정의 재설정 요청 차단 — 동작 방식은 미확인이라 시험 필요 ③ 위 강화 안.

## 7. 기간과 정리 (G4)

- 정해둔 기간: **25일 제안** (백업 보관 기간 자동 만료 25일과 맞춤). 사이트 공지로 알려요.
- 25일 뒤 운영자가 정리 함수를 실행: `quarantine`에 남은 행 삭제 + 그 사용자의 `auth.users` 삭제 (확인을 마친 사람은 `public`에 프로필이 있으므로 제외).
- 정리 전에 문의 메일함의 삭제 요청 목록과 한 번 더 대조해요.
- 대가: 25일 안에 돌아오지 않은 *실제 회원*도 삭제돼요 (재가입은 가능, 기록은 사라짐). 탈퇴자 되살림이 더 심각하다고 보고 선택한 방향이에요.

## 8. 구현 항목 (구현하기로 결정했을 때)

| 영역 | 항목 | 규모 |
|---|---|---|
| 복구 도구(평소에는 적용하지 않음) | 복원 순서 스크립트, `quarantine` 스키마 · 권한 · 이동/정리 함수 SQL | 작음~중간 |
| DB(평소에도 필요) | `public.restore_status()` · `confirm_restore()` (없으면 앱이 404 → "정상"으로 처리하도록 방어) | 작음 |
| 앱 | 로그인 후 `restore_status` 확인, "복구 확인" 화면 1개, 문구 | 작음 |
| Edge Function | `register-bakery`: 프로필 없으면 거부 / `delete-account`: 대기 계정 탈퇴 + `quarantine` 정리 | 작음 |
| Storage | 업로드 정책에 "활성 회원" 조건 추가 (마이그레이션) | 작음 |
| 시험 | PostgreSQL 역할 시험(PostgREST 대신 `anon`/`authenticated` 역할로 `quarantine` 접근 거부), 가짜 서버 화면 시험 | 중간 |

**두 가지 구현 시점:** ① 공개 전에 미리 (복구 때 바로 사용, 평소 코드에 복구 대응이 포함됨) ② 상황 B가 실제로 생길 때 (그만큼 복구가 늦어짐, 평소 코드가 단순). 사용자 결정 대기.

## 9. 가짜 데이터 시험에서 확인할 것 (README 8-1 확장)

PostgreSQL 임시 환경에서 확인할 수 있는 것:
1. `auth` 먼저 복원 → 마이그레이션 적용 순서에서 프로필 자동 생성이 일어나지 않는가
2. `public` → `quarantine` 이동 후 외래키 · 인덱스가 유지되는가
3. `confirm_restore()` 이동이 한 트랜잭션에서 성공하는가, 닉네임 충돌을 어떻게 처리하는가
4. `anon` / `authenticated` 역할로 `quarantine`을 읽거나 쓰려고 하면 **거부**되는가
5. 대기 사용자의 데이터가 랭킹 · 보기에 반영되지 않는가
6. 정리 함수 실행 후 `quarantine`과 해당 `auth.users`가 남지 않는가
7. **가짜 탈퇴자**(백업에는 있고 확인하지 않을 사람)가 대기 상태로 남았다가 정리로 사라지는가

PostgreSQL만으로는 확인할 수 없는 것 (시험용 Supabase 프로젝트 필요, 가짜 계정만 사용):
- Data API가 `quarantine`을 실제로 노출하지 않는지 (대시보드 설정)
- 복원된 계정의 실제 로그인, `banned_until` 동작, 밴 상태의 재설정 메일
- Storage 정책 변경의 실제 동작, `register-bakery` / `delete-account`의 동작

## 10. 남는 위험과 한계

- 이 설계는 **상황 B에만** 필요해요. 상황 A에서는 쓰지 않아요 (README 9장).
- 복원 직후부터 확인 전까지 `auth`에는 모든 복원 계정(탈퇴자 포함)의 이메일 · 해시가 존재해요. **연락 금지(G3)와 25일 정리로 노출 기간을 줄일 뿐 0으로 만들지는 못해요.** 이 점은 개인정보처리방침의 복원 관련 안내에 쓸지 법률 검토가 필요해요.
- 앱 밖(문의 메일)에서 받은 삭제 요청은 정리 전에 직접 대조해야 해요.
- 구현하지 않으면 상황 B에서는 이 설계 없이 서비스를 다시 열지 않는다는 규칙만 남아요 (복구가 느려져요).
