# DB 백업 설정 · 운영 · 복구 안내 (초안 2차)

> **상태: 아직 아무것도 설정하거나 실행하지 않았어요.** 이 문서와 `*.yml.draft` 두 파일은 계획이에요.
> PostgreSQL 설치, 비공개 저장소 생성, 실제 데이터 내려받기, 백업 실행, 자동화는 **모두 사용자 승인 뒤에** 해요.
> 개인정보처리방침에는 백업 보관 기간이 적혀 있어요 (현재 반영된 문구는 "최대 30일", 21일 삭제 시도 + 25일 자동 만료 방식으로 바꾸는 수정안은 승인 대기). **아래 설정이 끝나고 복구 시험이 성공하기 전에는 베타를 공개하지 않아요.**

## 1. 파일과 구성

| 파일 | 하는 일 |
|---|---|
| `backup-db.yml.draft` | **매일** DB를 내보내 → 암호화(키 2개) → Artifact로 올려요 |
| `cleanup-backups.yml.draft` | 매일 21일 넘은 백업을 **직접 삭제 시도**해요 (아래 3장) |
| 이 문서 | 설정 순서 · 한계 · 운영 · 복구 절차 |

```
Supabase DB ─(매일 pg_dump)→ 암호화(age, 받는 사람 2명) → Artifact (비공개 저장소 bakery-backups)
                                                              └→ 매일 cleanup: 21일 넘으면 삭제 시도 (+ 자동 만료 25일 설정)
```

**공개 저장소(`my-first-website`)에는 백업 파일도, 이 워크플로도 올리지 않아요.**

## 2. 무엇이 백업되고, 무엇은 안 되나

| 대상 | 백업 | 메모 |
|---|---|---|
| `public` 스키마 (일지 · 글 · 댓글 · 좋아요 · 신고 · 프로필 · 운영자 목록 …) | ✅ | 표 구조 + 데이터 + 함수 · 트리거 · 보기 |
| `auth.users`, `auth.identities` | ✅ 데이터만 | 이메일 · 비밀번호 해시 · 가입 정보 |
| 로그인 세션 · 갱신 토큰 · 일회용 토큰 · 인증 흐름 상태 · 감사 로그(IP) | ❌ 일부러 제외 | 백업에 꼭 필요하지 않은 민감 정보라서 뺐어요. 복구 후 모든 이용자는 **다시 로그인**해야 해요 |
| **사진 파일 (Storage `photos`)** | ❌ **미구현** | 5장 참고 |
| Edge Function 코드, 메일 템플릿, Auth 설정(Redirect URL 등) | ❌ | 이 저장소의 `supabase/` 폴더와 `docs/`에 코드가 있고, 대시보드 설정은 계획서에 적혀 있어요 |

### 인증 계정 복구 가능성 검토 (완전한 복구는 보장하지 않아요)

코드에서 확인한 사실:
- `public.profiles.id`는 `auth.users(id)`를 참조해요 (`0001_schema.sql`). `admins`(`0009`)도 마찬가지예요. → **계정이 먼저 있어야 앱 데이터를 넣을 수 있어요.**
- 사용자가 `auth.users`에 들어오면 트리거 `on_auth_user_created`가 `handle_new_user()`를 실행해서 **프로필을 자동으로 만들어요**. 닉네임은 `raw_user_meta_data`의 `nickname`을 쓰고, 없거나 형식이 틀리면 **그 사용자 추가 자체가 실패해요**. → 계정을 복원하면 프로필이 자동 생성되어, 백업의 `public.profiles` 데이터와 **같은 id로 충돌**할 수 있어요 (`created_at`도 달라져요).
- 일지 저장 등의 규칙(RLS)이 `auth.users.email_confirmed_at`을 봐요 (`is_email_verified`). → 이 값이 복원되어야 해요 (`auth.users`에 들어 있어요).

그래서 말할 수 있는 것과 없는 것:

| | |
|---|---|
| 말할 수 있는 것 | 이메일 · 비밀번호 해시 · 가입 시 닉네임/약관 기록(`raw_user_meta_data`) · 로그인 방식 정보는 백업 파일에 들어 있어요 |
| **보장할 수 없는 것** | ① 복원된 계정으로 **실제 로그인이 되는지** (Supabase 인증 서버가 복원된 행을 받아들이는지) ② 프로필 트리거 충돌을 **호스팅된 Supabase에서** 풀 수 있는지 (트리거를 끄거나 `session_replication_role`을 바꾸려면 슈퍼유저급 권한이 필요한데, `postgres` 계정은 권한이 제한돼요) ③ `auth.identities`를 `postgres` 계정으로 읽을 수 있는지 (권한 오류 보고가 있어요) ④ 이전 프로젝트와 다른 새 프로젝트로 옮길 때 `instance_id` 같은 값이 맞는지 |
| 그래서 | "백업이 있다 = 계정까지 완전히 복구된다"라고 **쓰지 않아요.** 복구 시험 결과가 나오기 전까지 계정 복구는 "미검증"이에요 |

**복구 시험의 한계도 미리 적어 둬요:** 내 PC의 임시 PostgreSQL은 *데이터가 들어가는지*(행 수, 외래키, 트리거 충돌, 비밀번호 해시 보존)만 확인해요. **Supabase 인증 서버로 로그인이 되는지는 확인할 수 없어요.** 로그인까지 보려면 별도의 시험용 Supabase 프로젝트(또는 로컬 Supabase)가 필요하고, 이것도 **가짜 계정으로만** 해요. 이 단계는 설치/생성 승인과 함께 따로 정해요.

## 3. 보관 기간 — 무엇을 하고, 무엇은 보장하지 못하나

**알아낸 사실**
- GitHub 문서는 `retention-days`로 만료일을 정할 수 있고, 저장소/조직 설정이 이보다 더 짧게 제한할 수 있다고만 해요.
- **만료되거나 삭제된 Artifact를 GitHub 내부에서 정확히 언제 지우는지는 공식 문서에 없어요.** (공식 문서는 "삭제하면 복구할 수 없다"까지만 말해요. 비공식 자료에는 "만료 즉시가 아니라 늦게 지워질 수 있다"는 언급이 있어요.)
- 그래서 어떤 설정으로도 "N일 뒤 물리적으로 지워진다"를 **보장할 수 없어요.** 우리가 정할 수 있는 것은 *삭제 시도 시점*과 *만료 설정*이에요.

**운영 방식 (이중 장치, 사용자 승인 2026-10-15)**
1. `cleanup-backups`가 **매일** 만든 지 **21일을 넘긴** Artifact를 공식 REST API로 **삭제 시도**해요. 삭제 뒤 기준보다 오래된 것이 남아 있으면 그 작업이 실패해서 알림이 와요.
2. `backup-db`가 올릴 때 `retention-days: 25`로 **자동 만료**를 설정해요 (1번이 실패할 때의 두 번째 장치).
3. 두 장치는 서로 독립이에요. 하나가 며칠 실패해도 다른 하나가 작동해요. 21일과 25일 사이의 4일은 "삭제 작업이 며칠 실패해도 점검에서 잡을 시간"이에요.

**이 방식이 보장하지 못하는 것**
- GitHub 내부에서 삭제된 파일이 완전히 사라지는 시점 (우리가 확인할 수 없어요)
- 두 장치가 동시에 실패하고 점검도 놓친 경우
- 내려받은 사본 (7장의 "당일 삭제"로 관리)
- **삭제 요청이 처리되면 목록에서 사라지고 내려받을 수 없게 되는지**는 첫 실행(dry-run 후 실제 삭제)에서 직접 확인해야 해요. 아직 안 해 봤어요.

**방침 · 약관 문구:** 정확한 원문은 `policy-wording-proposal.md`에 있어요 (승인 대기). 쓰지 않을 표현: "즉시 삭제", "완전히 삭제", "N일 뒤 지워져요"처럼 물리적 삭제 시점을 보장하는 말. 쓸 수 있는 표현: "삭제를 시도해요", "자동 만료되도록 설정해요", "삭제한 백업은 되살릴 수 없어요", "저장 서비스 내부에서 완전히 지워지는 시점은 그 서비스의 정책을 따라요".

## 4. 암호화 키 관리 (age, 키 2개)

**원칙**
- 백업은 **받는 사람 2명**(키 A, 키 B) 모두에게 암호화돼요. 어느 한쪽 키만 있어도 열 수 있어요. 하나를 잃어도 백업을 잃지 않아요.
- **공개키**(`age1…`)만 GitHub Secrets(`AGE_PUBLIC_KEY_1`, `AGE_PUBLIC_KEY_2`)에 넣어요. **개인키**(`AGE-SECRET-KEY-…`)는 GitHub에도, 이 저장소에도, 대화에도 절대 넣지 않아요.
- 워크플로는 키가 2개가 아니거나 서로 같으면 **백업 시작 전에 실패**해요 (키 하나짜리 백업이 만들어지는 걸 막아요).

**보관 위치 (이 프로젝트 폴더는 OneDrive 안이에요!)**
- 키는 **OneDrive 밖**에서 만들어요. 바탕화면 · 문서 · 사진 · 다운로드 폴더는 OneDrive가 자동으로 클라우드에 올릴 수 있으니 피해요. (예: `C:\bakery-keys\` 같은 동기화되지 않는 폴더에서 만든 뒤, 아래 보관 위치로 옮기고 원본은 삭제)
- 키 A: 비밀번호 관리자 (보안 메모) / 키 B: 오프라인 USB (집 등 다른 장소). **같은 곳에 둘 다 두지 않아요.**
- 키를 이메일 · 메신저 · 클라우드 문서에 붙여넣지 않아요.

**Windows에서 확인한 점 (2026-10-15 시험)**
- 설치: winget `FiloSottile.age` v1.3.2 (공식 GitHub 릴리스 zip, SHA256이 winget 매니페스트와 GitHub 릴리스 값에서 일치). 위치는 `%LOCALAPPDATA%\Microsoft\WinGet\Packages\FiloSottile.age_…\age\` 이고 OneDrive 밖이에요. 새 터미널에서 `age`/`age-keygen`이 바로 안 잡히면 터미널을 다시 열어요.
- **`age-keygen`의 "writing secret key to a world-readable file" 경고 — 원인을 확인했어요 (2026-10-15, 소스 코드 + 시험 결과).**
  - age v1.3.2 소스(`cmd/age-keygen/keygen.go`)의 조건은 `fi.Mode().IsRegular() && fi.Mode().Perm()&0004 != 0`(출력 파일의 "다른 사용자 읽기" 비트)이고, Windows용 예외 처리가 없어요. 파일은 `0600`으로 만들어요.
  - Go는 Windows에서 실제 접근 권한(ACL)을 읽지 않고 읽기 전용 속성만 보고 파일 모드를 **0666(일반) 또는 0444(읽기 전용)로 꾸며서** 알려줘요 (Go 문서/이슈 자료 기준). 두 값 모두 `0004` 비트가 켜져 있어서 **Windows에서는 항상 경고가 나와요.** 읽기 전용으로 바꿔도 사라지지 않아요.
  - 우리 시험에서도 폴더 접근을 내 계정만으로 제한했는데 경고가 나왔고, `icacls` 결과에도 내 계정(`USER`) 하나만 있었어요 → **경고는 실제 접근 상태와 무관한 오탐이에요.**
  - 그래서 Windows에서 이 경고는 키가 안전한지 알려주지 못해요. **진짜 확인은 `icacls <키 파일>`** 로 해요: 내 계정만 나오고 `Everyone`, `Users`, `Authenticated Users`가 없어야 해요.
  - 아직 직접 확인하지 못한 것: Go의 Windows 모드 계산을 소스 코드로 직접 읽지는 않았어요 (Go 관련 이슈 · 문서 요약 기준). 운영 키를 만들기 전에 이 점을 알고 진행하되, `icacls` 확인이 안전 판단의 기준이에요.
- **USB(대개 exFAT/FAT32)에는 파일 접근 권한(ACL)이 없어요.** 키 B를 USB에 평문으로 두면 USB를 주운 사람이 열 수 있어요. 키 파일 자체를 **비밀번호로 한 번 더 암호화**(`age -p`)해서 보관하고, 그 비밀번호는 키 A와 다른 곳(머릿속이나 비밀번호 관리자의 다른 항목)에 둬요. 이 방식도 운영 키를 만들기 전에 임시 키로 먼저 시험해요 (비밀번호 입력창이 PowerShell에서 뜨는지 포함).
- PowerShell 5.1에서 `age-keygen`의 경고 출력(stderr)은 `$ErrorActionPreference='Stop'`일 때 스크립트를 중단시켜요. 종료 코드(`$LASTEXITCODE`)로 성공을 판단해요.
- `C:\bakery-secure` 폴더는 접근 권한을 내 계정만으로 제한해 두었어요 (비어 있음). 이 도구 환경에서는 `C:\` 바로 아래 폴더 삭제가 시스템 경로 보호로 막혀서 상위 폴더는 남겨 뒀어요. 필요 없으면 탐색기에서 직접 지우셔도 돼요.

**키를 잃거나 유출되면**
| 상황 | 할 일 |
|---|---|
| 키 하나를 잃어버림 | 남은 키로 최근 백업이 열리는지 확인 → 새 키를 만들어 Secret을 교체 → 다음 백업부터 새 키로 암호화돼요. 이전 백업은 남은 키로만 열려요 |
| 키 하나가 유출됨 | 즉시 새 키로 교체. 유출된 키로 열 수 있는 **기존 백업(최대 25일치)** 은 남아 있으니, 비공개 저장소의 Artifact를 모두 삭제하고 새 키로 백업을 새로 만들어요. 내용이 정말 노출됐을 수 있으면 개인정보 유출 대응(방침의 문의처, 이용자 안내)을 검토해요 |
| 두 키를 모두 잃음 | 백업을 열 수 없어요. 새 키로 즉시 새 백업을 만들고 이전 백업은 삭제해요 |
| 분기마다 | 키 A, 키 B **각각으로** 가장 최근 백업이 복호화되는지 가짜 데이터 시험 때처럼 확인 (열어서 목차만 보고 바로 삭제) |

**기타 접근 통제**
- 비공개 저장소 Visibility가 **Private**인지 만든 직후와 분기마다 확인해요. 협업자 추가 금지, GitHub 계정에 2단계 인증을 켜요.
- `SUPABASE_DB_URL`(Session pooler 주소, 비밀번호 포함)은 Secret에만 넣어요. 공개 전에 `postgres` 비밀번호를 한 번 바꿔요. 읽기 전용 계정은 베타 이후 개선이에요.
- Actions 로그에는 개수와 파일 크기만 찍혀요 (개인정보 없음). 로그 보관 기간은 저장소 설정에서 줄일 수 있어요.

## 5. 사진 백업 — 미구현이에요

- **현재 사진 파일(Storage `photos`)은 백업되지 않아요.** Supabase의 "새 프로젝트로 복원"도 Storage 파일은 복사하지 않아요.
- DB를 복구하면 **일지/글은 돌아오지만 사진은 없는 상태**가 될 수 있어요 (화면에 깨진 이미지).
- 사진이 있는 곳과 크기: 공개 버킷 `photos`, 파일당 1MB 이하 JPEG/WebP, 경로는 `{user_id}/…`.

### 베타 공개 전, 사진 백업 없이 운영해도 되는가 (위험 재평가)

| 항목 | 평가 |
|---|---|
| 어떤 일이 생겨야 사진을 잃나 | ① 버킷/파일을 실수로 삭제 ② Supabase 장애 ③ 프로젝트 삭제 또는 장기 정지 ④ 앱/함수 버그로 폴더가 잘못 삭제됨 (탈퇴·신고 처리가 폴더를 지우는 코드가 있어요) |
| 발생 가능성 | 낮음~중간 (특히 ④는 직접 만든 삭제 코드가 있어 가능성이 있어요) |
| 피해 | 이용자가 올린 빵 사진 소실. 일지 텍스트와 EXP는 유지돼요. 개인에게는 의미가 큰 자료지만, 서비스의 핵심 데이터(계정/글)는 보호돼요 |
| 베타 규모 | 소규모 베타라면 **수용 가능한 위험**이라고 판단해요. 단, 아래 조건을 지킬 때만이에요 |
| 정식 운영 | 이용자와 사진이 늘면 **수용하기 어려워요.** 아래 "다시 판단할 기준"에서 정해요 |

**조건 (제안, 승인 필요)**
1. 사용자가 알 수 있게 알려요: 이용약관 베타 조항에 "사진 파일은 별도 백업이 없어 장애 시 복구되지 않을 수 있어요" 한 줄 추가 (지금은 안내가 없어요 → 숨기는 셈이 되지 않게)
2. 사진 총용량을 베타 첫 2주 동안 Supabase 대시보드(Storage)에서 확인해 기록해요
3. 복구 후 사진이 없는 일지가 깨져 보이지 않는지 한 번 확인해요 (**아직 확인하지 않았어요**)

**다시 판단할 기준:** 사진 총량이 수십 MB를 넘거나 / 가입자가 수십 명을 넘거나 / 이용자가 "사진이 사라졌어요"라고 문의하면 사진 백업을 설계해요.

**사진 백업을 하게 된다면 (참고 설계, 아직 구현 안 함)**
- 방법: Supabase의 S3 호환 주소 + rclone으로 버킷을 복사하거나, Supabase CLI의 `storage cp -r --experimental`
- 파일은 암호화되지 않은 채 내려오므로 `tar` 후 `age`(같은 키 2개)로 암호화
- 비밀값: Storage S3 접근 키 (권한이 넓음 → Secret에만, 공개 전 교체 계획)
- 복구: 버킷은 `0003_storage.sql`이 만들고, 같은 경로로 다시 올려요. DB 덤프에는 `storage` 스키마가 없으니 올릴 때 메타데이터가 새로 생겨요
- **한도 문제:** 비공개 저장소 Artifact 저장은 500MB(Packages와 공유)예요. DB 백업은 매일이지만 사진은 매일 전체를 복사하면 최대 약 21~25개 사본이 쌓여 사진 총량의 21~25배가 필요해요. 사진 백업은 DB와 **다른 주기(예: 주 1회)** 로 따로 설계하고, 그래도 사진이 커지면 다른 저장 장소를 정해야 해요
- 방침에 "사진 백업과 그 보관 기간"을 따로 써야 해요 (탈퇴자 사진이 백업 보관 기간 동안 남기 때문)

## 6. 비용 가능성 (GitHub Free 개인 계정)

| 항목 | 한도(공식 문서) | 예상 |
|---|---|---|
| 비공개 저장소 Actions 시간 | 월 2,000분 | 백업(매일, 설치 포함 3분 안팎) + 삭제 작업(매일, 1분 이내) = 월 100~150분 안팎으로 예상 (한도의 5~8%, **실제로 실행해 보고 확인**) |
| Artifact · Packages 저장 | 500MB 공유 | 매일 백업이라 암호화 사본이 **최대 약 21~25개** 동시에 쌓여요. 500MB ÷ 25 = 20MB이므로 **덤프 한 개가 약 18MB를 넘으면 한도에 닿아요** (베타 초기에는 훨씬 작을 것으로 예상, 첫 실행 후 크기 확인). 사진을 넣으면 가장 먼저 닿는 한도 |
- 결제 수단이 없으면 한도 초과 시 **사용이 막혀요**(과금 안 됨). 결제 수단을 등록했다면 초과분이 청구될 수 있어서, GitHub Billing에서 예산 0원/알림을 확인해요.
- Supabase 쪽 전송량(egress)도 덤프/사진 복사가 사용해요. Free 한도는 확인하지 못했으니 사진 백업 전에 대시보드에서 확인해요.

- [ ] 비공개 저장소 Actions 탭: `backup-db`가 **최근 7일 동안 매일 성공**했나? (매일 03:00 KST 실행, 빠진 날이 있으면 원인 확인)
- [ ] `cleanup-backups`가 최근 7일 **매일 성공**했나?
- [ ] Artifacts 목록에 **최근 7일치 파일**이 있고, 크기가 0이 아니고 서로 비슷한가? 전체 개수가 21개 안팎인가?
- [ ] **21일보다 오래된 Artifact가 없는가?** (있으면 cleanup 실패 → 바로 조치)
- [ ] 실패 알림 메일이 왔다면 원인 확인 (Supabase 프로젝트 일시 정지 → 백업이 계속 실패할 수 있어요)

점검을 놓치면 **백업이 몇 주 동안 0개**인 줄 모를 수 있어요. 달력 알림을 걸어 두세요.

### 매달 / 분기마다
- 매달: Actions 사용 시간과 저장 용량(Billing), Supabase 프로젝트 상태, Storage 사진 총용량
- 분기: 키 A · 키 B 각각으로 복호화 확인, 비공개 저장소가 Private인지 확인, `postgres` 비밀번호 교체 검토, 복구 시험 다시 해 보기

### 내려받은 백업 파일은 당일 삭제
백업 파일을 내려받는 것은 **복구 시험이나 실제 복구 때만** 해요. 내려받은 파일은 보관 기간 규칙 밖의 사본이라서 그날 안에 지워요.
1. 작업 폴더는 **OneDrive에 동기화되지 않는 곳**만 써요 (예: `C:\bakery-restore-temp\`). 바탕화면 · 문서 · 다운로드는 안 돼요. 브라우저로 받으면 다운로드 폴더(동기화될 수 있음)에 저장되므로, `gh run download -D C:\bakery-restore-temp`처럼 폴더를 지정하거나 브라우저의 "저장 위치 묻기"를 켜요.
2. 복호화한 파일(`.tar`, `.dump`)과 시험용 DB도 같은 폴더/임시 DB에만 둬요.
3. 작업이 끝나면 **폴더 전체와 임시 DB를 삭제**하고 휴지통도 비워요.
4. OneDrive 휴지통/버전 기록에 올라가지 않았는지 확인하고, 개인키 파일은 작업 폴더에 두지 않아요 (키 입력은 필요한 순간만).
5. 완료 기록: 날짜 · 목적 · 삭제 여부만 적어요 (**개인정보는 기록하지 않아요**).

## 8. 복구 시험 — 가짜 데이터로 먼저

**원칙: 실제 회원 데이터를 쓰는 시험은 가짜 데이터 시험이 성공한 뒤에만, 그것도 별도 승인 후에 해요. 운영 DB에는 어떤 시험도 하지 않아요.**

### 8-1. 가짜 데이터 시험 (먼저)
- 환경: 내 PC의 임시 PostgreSQL 17 (OneDrive 밖 폴더, **설치는 별도 승인**). 이 시험에는 인터넷 서비스(Supabase, GitHub)가 필요 없어요.
- 데이터: 누가 봐도 가짜인 값만 써요. 예) 이메일 `fake-1@example.invalid`, 닉네임 `가짜테스트1`, 일지/글 몇 개, 신고 1건. 실제 이메일 · 실제 닉네임 · 실제 일지 문구는 쓰지 않아요.
- 순서: ① 임시 DB에 `auth.users/identities`(단순 흉내)와 `public` 구조(`supabase/migrations/*.sql`)를 만들고 가짜 데이터를 넣기 → ② 워크플로와 **같은 명령**으로 두 덤프를 만들고 `age`(키 2개, 가짜 키)로 암호화 → ③ 키 A만으로, 키 B만으로 각각 복호화 → ④ 새 임시 DB에 복원
- 반드시 확인할 것: 행 수가 같은가 / `handle_new_user` 트리거로 프로필이 중복 생성되며 충돌하는가 (충돌을 어떻게 푸는지 기록) / 외래키 순서 / 비밀번호 해시와 `raw_user_meta_data` 보존 / `terms_version` 값 보존 / 복원 후 깨진 참조가 없는가
- **탈퇴자 걸러내기 시험:** 백업에는 있고 가짜 "운영 DB"에는 없는 가짜 탈퇴자(`fake-withdrawn@example.invalid`)를 일부러 만들고, 9장 상황 A의 가져오기 절차가 그 사람의 행을 **옮기지 않는지** 확인해요
- 알아낸 것을 `docs/backup/rehearsal-log.md`에 숫자와 결과만 기록해요 (개인정보 없음)

### 8-2. 인증 서버 로그인 시험 (선택, 가짜 계정 한정)
- 시험용 Supabase 프로젝트(또는 로컬 Supabase)에서 가짜 계정이 복원 후 실제 로그인되는지 확인. 이 시험 환경은 메일 발송(Brevo)을 연결하지 않아요. 끝나면 프로젝트 삭제.
- 이 시험을 하기 전에는 문서/방침에 "계정까지 복구돼요"라고 쓰지 않아요.

### 8-3. 실제 백업으로 시험 (마지막, 별도 승인)
- 위 두 시험이 성공한 뒤, 첫 실제 백업 하나로 같은 과정을 임시 환경에서만 해요. 끝나면 7장 "당일 삭제".

## 9. 탈퇴한 회원이 복원 때 되살아나지 않게 (탈퇴 장부는 도입하지 않아요)

> **매일 백업은 되살아날 수 있는 구간을 줄일 뿐, 이 문제를 해결하지 못해요.** 어떤 백업이든 "그 시점 이후에 탈퇴한 사람"이 들어 있고, 오래된 백업(예: 20일 전)을 복원하면 그 사이의 탈퇴자가 전부 되살아나요. 백업이 아무리 자주 돌아도 복원을 잘못하면 같은 일이 생겨요. 그래서 아래는 **백업 주기에 기대지 않는 복원 절차**로 막아요.

### 원칙 3가지
1. **운영 DB를 백업으로 통째로 덮어쓰지 않아요.** `pg_restore --clean`, `DROP`, `TRUNCATE`, 운영 DB를 대상으로 한 `pg_restore` 직접 실행은 금지예요. 복원은 항상 **격리된 스테이징 환경**에서 먼저 해요.
2. **살아남은 쪽이 명부예요.** 운영 DB에서 지금도 살아 있는 계정 목록(`auth.users`의 id 또는 `public.profiles`의 id)이 "현재 회원 명부"예요. 백업에서 옮기는 모든 행은 **이 명부에 있는 id의 것만** 옮겨요.
3. **명부를 만들 수 없으면(둘 다 잃었으면) 공개하지 않아요.** 복원한 계정은 본인이 다시 확인하기 전까지 화면에 보이지 않게 둬요 (아래 상황 B).

### 먼저 상황을 판정해요 (복원 전에 반드시)
| 상황 | 살아남은 명부 | 방법 |
|---|---|---|
| **A1** 일부 데이터만 잃음 (운영 `auth`와 `public`이 둘 다 살아 있음) | 운영 `auth.users` | `auth`는 **복원하지 않아요.** `public`의 잃은 행만, 명부에 있는 사용자 것만 옮겨요 |
| **A2** `auth`만 잃음 (`public`은 살아 있음) | 운영 `public.profiles` | 백업의 `auth.users/identities` 중 **`profiles`에 있는 id만** 복원해요 |
| **A3** `public`만 잃음 (`auth`는 살아 있음) | 운영 `auth.users` | 백업의 `public` 행 중 **`auth.users`에 있는 id의 것만** 복원해요 |
| **B** 둘 다 잃음 | **없음** | 아래 B 절차. **이 경우에만 되살림이 실제로 일어날 수 있어요** |

### 상황 A 절차 (명부가 있을 때)
1. 판정이 A인지 확인해요: 운영 DB에 접속해 `select count(*)`가 되는가? (되면 A, 접속 자체가 안 되거나 비어 있으면 B)
2. **명부 파일**을 만들어요: id(uuid)만 내보내요 (이메일 · 닉네임은 내보내지 않아요). OneDrive 밖 작업 폴더에 두고 당일 삭제해요.
3. 백업을 **스테이징**(임시 DB, 운영 아님)에 복원해요. 운영 DB에는 아직 아무것도 하지 않아요.
4. 스테이징에서 명부 밖 사용자의 행을 지우거나, 처음부터 명부 안 사용자의 행만 골라 옮길 세트를 만들어요.
5. **외래키 정합성을 확인해요**: 명부 안 사용자의 댓글이 *명부 밖(탈퇴한) 사용자의 글*을 가리키면 글이 없어서 넣을 수 없어요 → 그 댓글도 제외해요 (탈퇴 시 글과 함께 지워지는 규칙과 같아요). 좋아요 · 신고 · 방문 체크도 같은 방식으로 점검해요.
6. 숫자 점검: 가져올 행 수, **명부 밖 id가 0개인지**, 운영 회원 수가 복원 전후 같은지.
7. 운영 DB에는 **`INSERT`만** 해요 (이미 있는 행은 건드리지 않아요, 삭제 · 덮어쓰기 없음). 트랜잭션 안에서 하고, 점검이 맞을 때만 확정해요.
8. 끝나면 스테이징과 명부 파일을 삭제해요 (7장 "당일 삭제").

### 상황 B 절차 (명부가 없을 때: 운영 DB를 완전히 잃은 경우, 드묾)
"지금 누가 회원인지" 알 수 있는 곳이 없어요. 마지막 백업 이후 앱에서 탈퇴한 사람은 어디에도 기록이 없고 (`delete-account` 함수는 실패 단계만 로그에 남겨요), **백업 주기를 줄여도 이 구간은 0이 되지 않아요.**
1. **B0. 정말 둘 다 잃었는지 먼저 확인해요.** Supabase 대시보드 · 지원으로 프로젝트 복구 가능성부터 확인해요. 복구되면 A예요.
2. **B1. 새 프로젝트에 복원하고, 사이트는 점검 안내 상태로 둬요.** 프론트는 정적 사이트(GitHub Pages)라 점검 안내 화면은 언제든 띄울 수 있어요. 가입 · 로그인을 막아요.
3. **B2. 복원된 모든 계정을 "재확인 대기" 상태로 만들어요 (현재 구현 없음, 설계: `reconfirm-pending-design.md` — 격리 스키마 방식, 로그인 · API · 데이터 조회 차단).** 대기 계정의 일지 · 글 · 댓글 · 프로필은 **다른 사람에게 보이지 않아요.** 본인이 로그인해서 "계속 이용할게요"를 누르면 해제돼요. 탈퇴한 사람은 로그인하지 않으니 **보이지 않는 채로 남고**, 정해둔 기간(제안: 25일, 백업 보관 기간과 같게) 안에 확인하지 않은 계정은 운영자가 삭제해요.
4. **B3. 안내는 사이트 화면과 문의 메일 답변으로만 해요.** ⛔ 복원된 계정 전체에 메일을 보내지 않아요 (이미 탈퇴한 사람에게 다시 연락하게 돼요).
5. **B4. 문의 메일함의 탈퇴 · 삭제 요청 목록과 대조해서** 해당 계정을 즉시 삭제해요 (앱 밖에서 받은 요청만 대조할 수 있어요).
6. **B5. 위 B2가 준비되기 전에는 서비스를 다시 열지 않아요.**

**B2의 구현 필요성 (결정 필요, 아직 구현 안 함):** 컬럼 하나(예: `profiles.restore_pending_at`), 대기 계정 콘텐츠를 숨기는 화면/서버 규칙(RLS · 보기), 로그인 후 확인 화면, 기간 지난 대기 계정 삭제용 운영자 SQL이 필요해요. 선택지는 ① 공개 전에 미리 만들어 둔다 (개발 시간 필요, 복구 때 바로 사용) ② 상황 B가 실제로 생기면 그때 만든다 (복구가 그만큼 늦어짐) 두 가지예요. 어느 쪽이든 **B2 없이 복원본을 공개하는 것은 금지**예요.

**트레이드오프:** 대기 상태에서 정해둔 기간(제안 25일) 안에 돌아오지 않은 *실제 회원*도 삭제돼요. 개인정보 노출(탈퇴자 되살림)이 서비스 이용 손실(재가입)보다 더 심각하다고 보고 이 방향을 골랐어요. 사이트 공지로 알릴 수 있는 범위에서만 줄일 수 있어요.

### 운영 DB에 복원하기 전 필수 확인 (하나라도 "아니오"면 중단해요)
- [ ] **상황 판정을 글로 남겼나?** (A1/A2/A3/B, 판정 근거: 운영 DB 접속 여부, 어느 쪽이 살아 있는가)
- [ ] **복원이 정말 필요한가?** 일부만 잃었다면 임시 환경에서 필요한 행만 옮기는 방법(A)으로 해결 가능한가?
- [ ] 운영 DB에 대한 `--clean` · `DROP` · `TRUNCATE`가 계획에 **없는가?** (운영에는 `INSERT`만)
- [ ] **명부 파일을 만들었고, 가져올 데이터에 명부 밖 id가 0개임을 스테이징에서 확인했나?** (B라면 명부 대신 B2 "재확인 대기"가 준비되어 있나?)
- [ ] 같은 백업으로 **스테이징에서 먼저 복원 연습**을 해서 성공했나? (8-1 절차, 프로필 자동 생성 트리거 충돌 처리 방법이 시험으로 확인되어 있나)
- [ ] 백업을 복호화해 `pg_restore --list`로 정상 확인했고, 만든 날짜(=잃게 될 기간)를 확인했나? 그 이후의 **가입 · 리뷰 · 글 · 탈퇴**가 영향받는다는 점을 이해했나?
- [ ] 복원 직전 **현재 운영 DB의 안전용 백업**을 새로 만들었나? (이 백업도 보관 기간 규칙 대상, 복원이 끝나고 불필요하면 삭제)
- [ ] 복원 중 새 가입/글쓰기가 일어나지 않게 **점검 안내**를 띄웠나?
- [ ] 이용자 공지 문구에 "사진은 백업에 없어요", "모두 다시 로그인해야 해요"가 들어 있나? **복원된 계정에 메일을 보내지 않는다**는 점을 확인했나?
- [ ] 운영자(사용자)의 **명시적 승인**이 있나? (날짜 · 이유만 기록, 개인정보 기록 금지)
- [ ] 복원 후 확인 계획: 회원 수/리뷰 수 비교, 운영자 계정 로그인, 신고 화면, 사진 없는 일지 화면, 새 백업 1회 실행, 임시 파일 삭제(7장)

### 남는 위험 (정직하게)
- 상황 B에서 B2 없이 열면 탈퇴자가 되살아나요 → **B2 없이 열지 않는 것이 규칙이에요.**
- 상황 A에서도 명부 밖이라는 이유로 제외된 데이터(예: 아직 탈퇴하지 않았는데 운영 DB에서 실수로 사라진 계정)는 이 절차로 복구되지 않아요 → 그런 계정은 별도 판단이 필요해요.
- 앱 밖(문의 메일)에서 받은 삭제 요청을 복원 전에 처리하지 않았다면 되살아날 수 있어요 → 복원 전에 메일함 대조가 필수예요.
- 이 절차는 **아직 한 번도 실행해 보지 않았어요.** 8-1 가짜 데이터 시험에서 "가짜 탈퇴자가 걸러지는지"를 먼저 확인해요.
