# DB 백업 설정 · 복구 안내 (초안)

> **상태: 아직 아무것도 설정하지 않았어요.** 이 문서와 `backup-db.yml.draft`는 계획이에요.
> 개인정보처리방침에는 "백업본은 만든 날부터 30일 보관"이라고 적혀 있어요. **아래 1~5가 끝나고 6(복구 시험)이 성공하기 전에는 베타를 공개하지 않아요.**

## 방식 한눈에 보기

```
Supabase DB ──(주 1회 pg_dump, GitHub Actions)──> 암호화(age) ──> Artifact 30일 보관 ──> 자동 삭제
                    비공개 저장소 bakery-backups                       (복호화 키는 내 PC에만)
```

- 백업 대상: `public`(앱 데이터) + `auth`(가입 계정). **사진 파일(Storage)은 포함되지 않아요** (베타 이후 검토).
- 접속 주소 · 암호화 공개키는 **GitHub Secrets**에만 넣어요. 코드나 대화에 붙여넣지 않아요.
- **공개 저장소(`my-first-website`)에는 백업 파일도, 워크플로도 올리지 않아요.**

## 설정 순서 (각 단계는 사용자 승인 후에 진행해요)

| # | 할 일 | 누가 | 메모 |
|---|---|---|---|
| 1 | 비공개 저장소 `bakery-backups` 만들기 (Private 확인) | 사용자 승인 후 제가 `gh repo create --private` 또는 사용자가 웹에서 | 만든 뒤 Visibility가 Private인지 꼭 확인 |
| 2 | 암호화 키 쌍 만들기 (`age-keygen`) | **사용자 PC** | 개인키(`AGE-SECRET-KEY-…`)는 **GitHub에 넣지 않아요.** 비밀번호 관리자나 USB 등 2곳 이상에 보관. 잃으면 백업을 열 수 없어요 |
| 3 | Secret `AGE_PUBLIC_KEY` 등록 (공개키 `age1…`) | 사용자 | 저장소 Settings → Secrets and variables → Actions |
| 4 | Secret `SUPABASE_DB_URL` 등록 | **사용자만** | Supabase → Connect → **Session pooler** 주소(비밀번호 포함). 제가 보지 않아요. 아래 "접속 계정" 참고 |
| 5 | 워크플로 파일 넣기 (`backup-db.yml.draft` → 비공개 저장소의 `.github/workflows/backup-db.yml`) | 사용자 승인 후 제가 | 넣기 전에 한 번 더 같이 읽어 봐요 |
| 6 | **첫 수동 실행 + 복구 시험** | 사용자 승인 후 | 아래 "복구 시험". 이때 처음으로 실제 데이터를 내려받아요 |
| 7 | 방침 · 계획서 최종 확인 | 제가 | 시험 결과를 `docs/beta-launch-plan.md` 11번에 기록 |

### 접속 계정에 대해
- 가장 간단한 건 기본 `postgres` 계정이에요. 다만 **권한이 커서** 유출되면 위험해요 → Secrets에만 두고, 공개 전 점검 때 비밀번호를 한 번 바꿔요.
- 더 안전한 방법은 읽기 전용 계정(`public`, `auth` SELECT만)을 따로 만드는 거예요. 설정이 늘어서 **베타 이후 개선**으로 두자고 제안해요. (원하시면 SQL을 만들어 드릴게요)

## 30일 보관이 지켜지는 방식 · 한계

- Artifact는 `retention-days: 30`이 지나면 GitHub가 자동 삭제해요. 설정을 바꿀 때는 **방침의 "30일"도 같이 바꿔요.**
- GitHub 설명상 만료 삭제는 즉시가 아니라 그 무렵에 이뤄질 수 있어요. "정확히 30일"이 아니라 "최대 30일 안팎"이라는 점은 방침 문구("30일이 지나면 삭제")와 어긋나지 않는지 시험 때 확인해요.
- 주 1회라서 한 번에 최대 4~5개가 동시에 남아요.
- 이용자가 탈퇴하면 DB에서는 바로 지워지고, **이미 만들어진 백업에는 최대 30일 남아요** (방침에 쓴 그대로예요). 복구할 때 탈퇴자를 되살리지 않도록 아래 "복구할 때 주의"를 지켜요.
- 비공개 저장소의 Actions **로그**는 별도 보관 기간(기본 90일)이 있어요. 워크플로는 개인정보를 로그에 찍지 않도록 썼어요(개수와 파일 크기만). 저장소 설정에서 로그 보관 기간을 줄일 수 있어요.

## 복구 시험 (6단계에서 실제로 해 봐요)

목표: "백업 파일이 실제로 열리고, 안의 데이터가 맞는지" 확인. **운영 DB에는 절대 복원하지 않아요.**

1. Actions 탭 → `backup-db` → Run workflow (수동 실행) → 성공 확인
2. Artifact `bakery-db-backup` 다운로드 (zip 안에 `.dump.age`)
3. 내 PC에서 복호화: `age --decrypt -i <개인키 파일> -o backup.dump bakery-db-….dump.age`
4. **시험용 빈 DB**에 복원 (새 Supabase 프로젝트 또는 로컬 PostgreSQL 17)
   - `pg_restore --no-owner --no-privileges --dbname "<시험 DB 주소>" backup.dump`
   - `auth` 스키마는 Supabase가 이미 만들어 둔 표와 겹쳐서 오류가 날 수 있어요 → 오류 내용을 보고 `--schema=public`만 먼저, 그다음 `auth` 데이터만(`--data-only --schema=auth`) 따로 넣는 방식으로 조정해요. **이 부분은 실제로 해 보기 전에는 확정할 수 없어요.**
5. 확인: 사용자 수 · 리뷰 수 · 글 수가 운영 DB와 대략 맞는지 (숫자만 비교, 내용은 보지 않아도 돼요)
6. 시험이 끝나면 **복호화한 파일과 시험 DB를 삭제**해요 (개인정보가 들어 있어요)

### 복구할 때 주의 (실제 사고 시)
- 복구 뒤에는 **탈퇴 요청을 한 사용자가 되살아나지 않았는지** 확인하고, 있으면 다시 삭제해요 (탈퇴 이력은 백업 시점 이후의 일이라 복원본에 없어요).
- 사진 파일은 백업에 없어요. 복구 후 사진이 없는 일지가 생길 수 있어요.

## 아직 검증하지 않은 것 (정직하게)

- `pg_dump` 17이 이 프로젝트의 Supabase 서버 버전과 호환되는지 (서버가 17보다 높으면 실패해요 → 첫 실행에서 확인)
- Session pooler 주소로 `pg_dump`가 되는지 (안 되면 Direct connection / IPv4 설정 확인)
- `auth` 스키마까지 한 번에 복원되는지 (위 4번)
- 워크플로 문법 (GitHub에서 처음 돌려 봐야 확실해요)
- 만료된 Artifact가 실제로 사라지는 시점
