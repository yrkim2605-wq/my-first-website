# 베타 공개 준비 계획

> **main 병합과 실제 배포는 사용자가 따로 승인하기 전까지 하지 않아요.**
> 이 문서는 "무엇이 끝났고, 무엇을 사용자가 직접 설정해야 하고, 어떤 순서로 공개하는지"를 모아 둔 계획서예요.
> 작성일: 2026-10-14 / 브랜치: `rpg-redesign` (main은 Supabase 5단계에서 멈춰 있고, 운영은 로컬 모드)

## 1. 구현이 끝난 것 (공개 전 필수 6가지)

| # | 기능 | 서버 변경 | 자동 시험 | 실서버 확인 |
|---|---|---|---|---|
| 1 | 비밀번호 찾기 · 재설정 | 없음 (Supabase Auth 기능 사용) | 저장소 시험 12개 | ❌ 메일 발송 필요 (SMTP 설정 후) |
| 2 | 회원 탈퇴 (계정 + DB 기록 + 사진 파일) | Edge Function `delete-account` **배포 필요** | 함수 시험 23개 + 저장소 시험 8개 | ❌ 함수 배포 후 |
| 3 | 개인정보처리방침 · 이용약관 초안, 가입 동의, 푸터 링크 | 없음 | 문서 시험 18개 + 동의 시험 5개 | 해당 없음 (법률 검토 필요) |
| 4 | 글 · 댓글 · 일지 신고 | **마이그레이션 `0009_reports.sql` 적용 필요** | PGlite(진짜 Postgres) 보안 시험 59개 + 저장소 시험 39개 | ❌ 0009 적용 후 |
| 5 | 운영자 신고 처리 (`/admin/reports`) | `0009` + **`0010_storage_admin.sql`** + 운영자 등록 | 위 시험에 포함 | ❌ 0009 · 0010 적용 + 운영자 등록 후 |
| 6 | ErrorBoundary · 404 · 쉬운 오류 안내 | 없음 | 시험 23개 (+ 브라우저에서 실제 확인) | ✅ 브라우저 확인 완료 |

**실서버에서 확인하지 못한 이유**: 아직 서버에 0009 · 0010 · 새 함수가 없고, 계정 · 메일은 제가 만들 수 없어요. 화면은 가짜 서버(`supabase/tests/ui-fake`)로, 서버 규칙은 PGlite로 확인했어요. **서버 설정을 마친 뒤 4장의 "실서버 시험"을 꼭 해 주세요.**

### 이번 구현의 알아 둘 점

- **탈퇴**: 사진 파일 삭제 → 계정 삭제 순서예요. 사진 삭제가 실패하면 계정은 그대로이고 다시 시도할 수 있어요. 계정이 지워지면 리뷰 · 글 · 댓글 · 좋아요 · 체크가 연쇄로 지워지고, **내 글에 달린 다른 사람의 댓글도 함께 지워져요.**
- **탈퇴 본인 확인**: 비밀번호를 다시 입력해 로그인한 직후(10분 이내)의 세션만 허용해요. 서버가 로그인 토큰의 `amr`(인증 시각)을 확인해요. 실서버 토큰의 `amr` 확인은 **시험 계정 탈퇴가 성공해서 통과한 것으로 확인했어요** (2026-10-15, 로컬). 없었다면 탈퇴가 "비밀번호 다시 확인" 오류로 막혔을 거예요 — 보안상 안전한 쪽으로 실패하는 설계예요.
- **신고**: 신고자는 4칸(대상 · 사유 · 설명)만 쓰고, 신고자 · 상태 · 작성자 · 내용은 서버가 정해요. 내 글 신고 금지, 같은 대상 중복 금지, 하루 20건 제한이 서버 규칙이에요.
- **운영자**: `admins` 표는 앱에서 읽거나 쓸 수 없어요. 운영자는 **SQL Editor에서만** 등록해요. 일반 사용자가 운영자가 될 길이 없어요 (시험으로 확인).
- **리뷰를 삭제하면** 그 사용자의 EXP는 다시 계산돼서 줄어들어요 (EXP를 저장하지 않고 리뷰에서 계산하는 설계 때문).
- **사진 파일**: 운영자가 글을 삭제 처리하면 화면이 파일도 지워 봐요. 실패하면 경고에 파일 경로가 나와요 → Storage에서 직접 지워 주세요.
- **비밀번호 재설정 링크**는 메일을 요청한 **같은 브라우저**에서만 열려요 (PKCE 방식). 다른 기기에서 열면 "링크가 만료됐어요"가 나와요 — 안내 문구에 적어 뒀어요.

### 배포할 때 주의 (Edge Function)

- **대시보드에서 함수 코드를 다시 배포하면 Verify JWT가 "켜짐"으로 되돌아갈 수 있어요.** `register-bakery`가 실제로 그랬어요. 두 함수(`register-bakery`, `delete-account`)는 모두 함수가 스스로 토큰을 검증하므로 **꺼 둔 상태가 기준**이에요.
- 배포 뒤 확인법: 로그인 없이 `POST`를 보내서, 응답이 **앞단**(`code: UNAUTHORIZED_…`, "Missing authorization header")이면 켜짐이고, **함수**(`error.code: NOT_SIGNED_IN`)이면 꺼짐이에요. `node supabase/check-live.mjs`가 응답 모양까지 확인해요.
- **메일 템플릿(Confirm sign up 등)에 잘못된 HTML을 넣으면 가입 자체가 500으로 실패해요** (Auth Logs: `html/template: ... in unquoted attr`). 템플릿을 바꿀 때마다 가입 · 재설정을 한 번씩 실제로 시험해요.
- 설정 변경 직후에는 함수가 다시 뜨면서 **503이 한두 번 나올 수 있어요.** 반복되면 Edge Functions → 해당 함수 → Logs를 확인해요.

## 3. 법률 문서: 사용자가 확인해야 하는 항목

본문은 이 앱의 실제 데이터 흐름(수집 항목, 공개 범위, 위탁 업체, 삭제 방식)을 따라 쓴 **초안**이에요. 전문가(법률) 검토를 받은 문서가 아니에요. 아래 값은 **임의로 만들지 않고 비워 뒀어요** (`src/constants/legalInfo.js`).

| 항목 (키) | 무엇을 적나 | 어디서 알 수 있나 | 상태 |
|---|---|---|---|
| 운영자 이름 (`operatorName`) | 운영자(개인/사업자) 이름 | 사용자 결정 | ✅ 반영 |
| 문의 이메일 (`contactEmail`) | 문의 · 신고 · 개인정보 요청을 받을 주소 | 사용자 결정 | ✅ 반영 |
| 개인정보 보호책임자 (`privacyOfficer`) | 이름과 연락처 | 사용자 결정 | ✅ 반영 |
| 시행일 (`effectiveDate`) | 약관 · 방침이 시작되는 날 | 사용자 결정 | ✅ 반영 |
| 데이터 저장 지역 (`dataRegion`) | Supabase 프로젝트 지역 | Project Settings | ✅ 서울 (ap-northeast-2), DB 위치만 · 2026-10-15 |
| 메일 발송 서비스 (`mailProvider`) | 인증 · 재설정 메일 업체 | SMTP 설정 후 | ✅ 반영 |
| 메일 서비스 처리 위치 (`mailProviderRegion`) | Brevo가 메일 주소를 처리하는 서버 위치. Supabase DB 위치와 별개 | Brevo 공식 문서 · 계정 설정 | ✅ 주로 EU(프랑스 · 독일 · 벨기에), 일부 하위 업체는 미국 등 (Brevo 공식 문서, 2026-10-15) |
| 가입 가능 최소 나이 (`minimumAge`) | 예: 만 14세 이상 | 사용자 결정 (법률 검토) | ✅ 만 14세 이상 (안내 문구만 — 가입 화면의 나이 확인 기능은 없음) |
| 접속 기록 보관 기간 (`logRetention`) | 서버 로그 보관 기간 | Supabase 설정 확인 | ✅ 약 1일 (Supabase Free 기준) |
| 메일 발송 기록 보관 기간 (`mailLogRetention`) | Brevo 발송 로그 보관 기간 (Supabase 로그와 별개) | Brevo 설정 | ✅ 1개월 · All senders · 본문 미리보기 저장 안 함 (2026-10-15) |
| 백업 보관 기간 (`backupRetention`) | 탈퇴한 정보가 백업에 남는 기간 | 백업 방식 결정 후 | ✅ 최대 30일 (정기 db dump 방식) — 실제 절차는 11번에서 만들어야 해요 |
| 신고 기록 보관 기간 (`reportRetention`) | 처리된 신고를 보관하는 기간 | 사용자 결정 | ✅ 처리가 끝난 날부터 1년 |
| 관할 법원 (`jurisdiction`) | 분쟁 시 관할 | 사용자 결정 (법률 검토) | ✅ 특정 법원 미지정, "민사소송법 등 관계 법령에 따릅니다" (사용자 지정 문구, 2026-10-15) |

값이 모두 채워지면 문서 위의 "초안" 경고가 자동으로 사라져요. 약관을 바꾸면 `LEGAL_VERSION`도 바꿔 주세요 (가입할 때 동의한 버전이 계정에 기록돼요).

> 가입 동의는 **화면과 저장소 코드**가 강제해요. 서버(DB)가 동의 기록 없는 가입을 거부하게 하려면 마이그레이션이 한 번 더 필요해요 (선택 사항, 원하시면 제안할게요).

## 5. 공개 순서 · 롤백 · 운영

### 공개 순서 (모두 사용자 승인 후)
1. 2장의 1~9번 설정 완료, 4장 시험 통과
2. `git tag main-before-account-mode main`
3. `deploy.yml`에 계정 모드 환경변수 추가 (2장 8번)
4. `rpg-redesign` → `main` 병합 (PR 권장) → 자동 배포
5. 배포 직후 4장의 핵심 항목을 운영 주소에서 한 번 더 (가입 · 로그인 · 신고)

### 롤백
- 코드: `git revert`로 병합을 되돌리거나, 태그 `main-before-account-mode`로 복원 후 재배포
- 서버 규칙(0009 · 0010): 새 표 · 함수 추가라서 기존 기능에는 영향이 없어요. 롤백이 꼭 필요하면 `reports` · `admins` 표와 함수를 지우면 돼요 (사전에 백업)

### 운영: 신고가 들어왔을 때
1. 운영자 계정으로 로그인 → 주소 뒤에 `#/admin/reports` (메뉴에는 보이지 않아요)
2. 신고 내용(신고 당시 앞부분이 저장돼요)과 "원문 보러 가기"로 확인
3. 문제 없음 → **반려** / 규칙 위반 → **삭제하고 처리** (같은 글의 다른 열린 신고도 함께 처리돼요)
4. 사진 파일 경고가 나오면 Supabase → Storage → photos에서 표시된 경로의 파일을 삭제
5. 처리 기록은 "삭제 처리 / 반려" 탭에서 다시 볼 수 있어요
- 반복 위반 사용자의 계정 제한은 아직 화면이 없어요 → 필요하면 Authentication → Users에서 직접 처리 (베타 후 개선 항목)
- **운영자 계정 보안**: 강한 비밀번호 사용, 가능하면 별도 이메일. 운영자 목록은 SQL로만 바꿀 수 있어요

### 운영: 오류 확인
- 브라우저: 오류는 콘솔과 `bakery:client-error` 이벤트로 남아요 (수집 서비스는 아직 없어요 — 베타 후 Sentry 등 도입 검토. 붙일 곳은 `src/utils/reportClientError.js` 한 곳이에요)
- 서버: Supabase → Logs (API · Auth), Edge Functions → 각 함수 → Logs (`[register-bakery]`, `[delete-account]` 실패 단계가 남아요)
- 이용자에게는 쉬운 안내만 보이고, 원인은 개발 콘솔의 `debug.operatorHint`로 확인해요

### 운영: 백업 · 복구 · 사용량
- Free 플랜은 자동 백업이 없는 것으로 알고 있어요 (공식 문서로 확인해 주세요). 정기 `pg_dump`(예: GitHub Actions, 비공개 저장소)를 권해요
- 사진(Storage)은 DB 백업에 포함되지 않아요 → 별도 보관 방법을 정해야 해요
- 복구 절차는 한 번 연습해 두면 좋아요 (새 프로젝트에 복원)
- Free 한도(DB · 파일 저장 · 전송량), 프로젝트 자동 정지(일정 기간 활동이 없으면), 카카오 쿼터는 베타 중 주 1회 확인하세요. 사진이 가장 먼저 한도에 닿을 거예요

## 6. 베타 공개 후 개선 가능 (이번 범위 밖)

- 가입 인증 · 비밀번호 재설정 **메일 디자인 개선** (지금은 단순 템플릿. 복잡한 HTML은 템플릿 파싱 오류로 가입이 500이 된 적이 있어 한 번에 조금씩, 가입 시험으로 확인하며)
- **오류 문구 실제 유형 점검**: `authMessages.js`의 502/503/504 분기(9e83411)는 추측으로 만들었어요. 실제 SMTP 실패는 Auth 로그 500이었는데 화면에는 "서버에 연결하지 못했어요"가 떴어요(브라우저가 오류 응답을 못 읽었을 가능성, 미확인). 개발자 도구 Network 탭에서 500 응답이 어떻게 보이는지 확인한 뒤, 서버 쪽 실패(메일 발송 실패 포함)를 별도 안내로 나눌지 결정

- 사용자별 사진 개수 제한 · 오래된 고아 파일 정리
- `register-bakery` 호출 제한을 DB 기반으로 (지금은 함수 인스턴스별 "최선의 노력")
- 닉네임 욕설 · 사칭 필터, 계정 이용 제한(정지) 화면, 신고 알림(메일)
- 서버(DB)가 약관 동의 없는 가입을 거부하는 규칙
- 접근성 점검(스크린리더 · 키보드 · 색 대비), 성능 측정
- 오류 수집 서비스 도입, 운영 대시보드(가입자 · 신고 수)
- 법률 전문가 검토 반영 (약관 · 방침 정식판)
