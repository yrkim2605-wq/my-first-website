# 8단계 · 리뷰 저장 실패 원인 구분 + 리뷰 최소 글자 수

> 상태: 구현 + 자동 검증 완료 / **실제 실패 원인은 아직 확정하지 못했어요 → 화면의 새 안내문(또는 콘솔 로그)으로 확인해야 해요**
> 보안 정책(RLS 등)은 건드리지 않았어요. 0006은 “검사”를 더하는 마이그레이션이라 오히려 더 엄격해져요.

## 1. 저장 실패 — 지금까지 알아낸 것

“저장하지 못했어요. 잠시 후 다시 시도해 주세요.”는 **원인을 알 수 없을 때 나오는 마지막 기본 문구**였어요.
리뷰 저장은 3단계로 진행돼요.

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| ① `register` | 처음 쓰는 빵집이면 서버 함수 `register-bakery`가 카카오에 “진짜 빵집인지” 확인하고 등록 | 함수/카카오 문제 |
| ② `photo` | 사진이 있으면 업로드 | 사진/저장소 문제 |
| ③ `insert` | `reviews` 표에 일지 저장 (EXP는 서버가 계산) | 권한/제약/서버 설정 문제 |

확인한 것 (로그인 없이 읽기만 한 진단, 가짜 계정 생성 없음)
- `register-bakery` 함수는 **배포돼 있고**, 접속(CORS)도 되고, 필요한 서버 설정(카카오 REST 키 등)도 **비어 있지 않아요**.
- 예전 코드는 함수가 돌려주는 **500(서버 내부/설정), 502(카카오 연결 실패), 413**, 그리고 “서버에 아예 닿지 못함”을 해석하지 못하고 전부 기본 문구로 뭉뚱그렸어요. 새 빵집의 첫 일지는 반드시 이 함수를 거치므로 **가장 의심되는 지점**이에요. (확정은 아니에요 — 이 환경에서는 로그인한 요청을 재현할 수 없어요)
- 그 외 DB 쪽(권한, 제약, 서버 표 구조 불일치)도 이제 구분해서 알려줘요.

## 2. 이제 화면에 나오는 안내 (원인 → 누가 고치나)

| 안내문(요약) | 원인 | 해결 |
|---|---|---|
| 카카오의 빵집 확인 서비스에 연결하지 못했어요 | 함수가 카카오 호출에 실패(502) | 카카오 개발자 콘솔에서 **REST API 키**가 맞는지, 앱에서 **카카오맵(로컬 API) 사용 설정**이 켜졌는지 확인 → Supabase Edge Functions의 `KAKAO_REST_API_KEY` 시크릿 재확인 |
| 빵집 확인 서버의 설정이 끝나지 않았어요 | 함수에 필요한 시크릿 없음(500 NOT_CONFIGURED) | Supabase → Edge Functions → Secrets에 `KAKAO_REST_API_KEY` 등록 |
| 빵집 확인 서버에서 문제가 생겼어요 (오류 코드: register/500/…) | 함수 내부 오류 | Supabase → Edge Functions → register-bakery → **Logs** 확인 |
| 빵집 확인 서버에 연결하지 못했어요 | 인터넷 끊김/함수 미배포/접근 차단 | 함수 배포·**Verify JWT 끔** 상태 확인 |
| 실제 제과·베이커리로 확인되지 않았어요 등 | 카카오가 그 장소를 빵집으로 보지 않음(400) | 다른 빵집으로 시도 |
| 저장할 권한이 없어요 | `reviews` 삽입이 RLS에 막힘(42501) | 로그인/이메일 인증 확인. 계속되면 알려 주세요(정책은 임의로 풀지 않아요) |
| 서버 데이터베이스 설정이 앱과 맞지 않아요 (마이그레이션 0001~0006) | 서버 표/칸이 코드와 다름(PGRST204 등) | 빠진 마이그레이션 적용 |
| 내용이 너무 짧아요/너무 길어요 | 글자 수 규칙 | 아래 3장 |
| 이미 이 빵집에 기록을 남겼어요 | 한 빵집 1개 규칙 | 기존 일지를 고쳐 쓰기 |
| 저장하지 못했어요. … **(오류 코드: insert/XXXXX)** | 정말 처음 보는 오류 | **이 코드(괄호 안)를 알려 주세요** |

### 2-1. “빵집 확인 서버에 연결하지 못했어요 (상태=null)”가 나올 때

`상태=null`은 **요청이 서버 함수에 닿기 전에 브라우저에서 실패**했다는 뜻이에요. (서버가 에러를 돌려준 게 아니에요)
서버 쪽은 이렇게 확인했어요 (로그인 없이 읽기만 한 진단):
- 함수는 배포돼 있고, 사전 요청(CORS)에도 정상 응답해요. 필요한 서버 설정값도 들어 있어요.
- 함수의 **Verify JWT가 지금 켜져 있어요** (가짜 토큰을 게이트웨이가 거절). 보안상 문제는 아니에요(오히려 더 엄격). 이 함수는 스스로도 로그인을 검사해서 켜져 있어도 꺼져 있어도 안전해요.

그래서 이제 앱이 실패 순간에 **스스로 원인을 가려서** 안내해요 (로그인 정보 없는 단순 요청을 한 번 더 보내 서버에 닿는지 확인해요. 아무것도 바뀌지 않는 401 응답이에요).

| 화면 안내 | 진단 결과 | 뜻 | 해볼 것 |
|---|---|---|---|
| “이 브라우저에서 서버(Supabase)에 연결되지 않아요” | 단순 요청도 실패 | 이 브라우저가 서버에 못 닿아요 | 인터넷/VPN 확인, **광고·보안 차단 확장 프로그램 끄기**, **시크릿 창**에서 시도, 다른 네트워크(휴대폰 핫스팟) |
| “서버는 응답하는데, 로그인 정보가 담긴 요청이 서버에 닿기 전에 막혔어요” | 단순 요청은 응답 | 서버는 살아 있고, 로그인 정보(Authorization 헤더)가 담긴 요청만 실패 | 로그아웃 → 다시 로그인 후 재시도. 계속되면 아래 Network 탭 내용을 알려 주세요 |
| “빵집 확인 서버에 연결하지 못했어요 (일반)” | 진단 불가 | 함수 주소를 알 수 없음 | — |

개발 환경의 오류 상자와 콘솔에는 `원인=…`(원래 오류, 예: TypeError: Failed to fetch)과 `진단=…`이 같이 나와요.

**30초 자가 점검**: 브라우저 새 탭에서 아래 주소를 열어 보세요. 글자(JSON)가 보이면 이 브라우저는 서버에 닿는 거예요.
`https://ujgklqbtoimazuzwjuhv.supabase.co/functions/v1/register-bakery`
→ `{"error":{"code":"METHOD_NOT_ALLOWED","message":"POST만 쓸 수 있어요."}}` 또는 `NOT_SIGNED_IN`이 보이면 정상 도달이에요. 아무것도 안 열리거나 오류 화면이면 이 브라우저/네트워크 문제예요.

**정확히 보려면 (F12 → Network 탭)**: 저장을 다시 눌러서 `register-bakery` 줄을 찾고 → **Status**(빨간색이면 `(failed)`/`CORS error`/`blocked` 등), 그 줄을 눌러 **Headers**(Request URL, Status Code)와 **Console 탭의 빨간 글**(예: `blocked by CORS policy: …`)을 알려 주세요.

### 브라우저에서 원인 확인하기 (개발 환경)
1. 로컬(`npm run dev`)에서 저장을 다시 시도해요.
2. 키보드 **F12 → Console** 탭을 열어 `[빵덕후 저장 오류]`를 찾아요. 아래가 한 줄로 나와요.
   `step`(어느 단계) · `source`(function/database) · `status`(HTTP 상태) · `code` · `message` · `details` · `hint` · `serverCode`
3. 같은 정보가 리뷰 창 오류 상자 아래에 작게 `[개발용] 단계=… 출처=… 상태=… 코드=…`로도 보여요. (배포본에는 안 나와요. 로그인 토큰·키는 어디에도 출력하지 않아요)

> 그 한 줄(또는 화면의 오류 코드)을 알려 주시면 정확한 원인을 바로 좁힐 수 있어요.

## 3. 리뷰 글자 수 규칙

- **최소 20자**: 띄어쓰기·줄바꿈·탭·눈에 안 보이는 공백(NBSP, 전각 공백, 너비 0 공백 등)을 **뺀** 실제 글자 수
- **최대 500자**: 앞뒤 공백을 뺀 전체 글자 수 (예전부터의 규칙 그대로)
- 이모지 1개 = 1자
- 입력창 아래: 왼쪽에 안내, 오른쪽에 현재 글자 수 `15/500` (적은 전체 글자 수)
  - 비어 있을 때: “공백을 뺀 20자 이상 적어주세요”
  - 20자 미만: **“조금만 더 자세히 적어주세요! (N자 남음)”**
  - 충족: “충분히 적었어요!”
- 20자 미만이면 **저장 버튼이 잠겨요.** 고쳐 쓸 때(수정)도 같아요.
- 서버(0006)가 **화면과 똑같은 규칙으로 한 번 더 검사**해서, 화면을 우회해도 저장되지 않아요.
- **기존에 저장된 20자 미만 일지는 삭제·변경하지 않아요.** 별점/사진만 고치는 요청은 막지 않고, “내용”을 고칠 때만 새 규칙을 적용해요.
- EXP 지급·하루 EXP 한도(100)·하루 작성 한도(20개)는 **그대로**예요. 규칙에 걸려 거절된 일지는 저장도, EXP 계산도, 하루 한도 소모도 없어요.

> 참고(해석): “공백을 제외한 실제 내용 기준 최소 20자, 최대 500자”에서 **최소는 공백을 뺀 글자 수**, **최대는 기존처럼 앞뒤 공백을 뺀 전체 글자 수(500)**로 적용했어요. 최대도 공백을 뺀 기준으로 바꾸고 싶으면 알려 주세요.

## 4. 0006 마이그레이션 적용 방법 (초보자용)

> 0006은 **검사용 함수 1개와 트리거 2개**만 추가해요. 표 구조와 기존 데이터는 바꾸지 않고, 여러 번 실행해도 안전해요.
> 적용 전에도 화면/앱 쪽 검사는 동작하고, 적용하면 서버도 막아요.

1. Supabase 대시보드 → 프로젝트 → **SQL Editor** → **New query**
2. `lecture1/my-bakery-review/supabase/migrations/0006_review_content.sql` 전체를 복사해서 붙여넣기
3. **Run** → `Success. No rows returned`
4. (확인) 새 쿼리에서 실행:
   ```sql
   select public.review_meaningful_length('가 나 다') as 공백뺀글자수;   -- 3
   select tgname from pg_trigger where tgrelid = 'public.reviews'::regclass and not tgisinternal order by tgname;
   ```
   트리거 목록에 `reviews_a_validate_content_ins`, `reviews_a_validate_content_upd`가 보이면 성공이에요.

되돌리기(보통 필요 없음): `drop trigger reviews_a_validate_content_ins on public.reviews; drop trigger reviews_a_validate_content_upd on public.reviews;`
